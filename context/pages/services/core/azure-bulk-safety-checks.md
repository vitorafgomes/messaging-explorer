# Core: Azure bulk safety checks

One topic of [[pages/services/core|Core]]; the scan loops themselves are on [[pages/services/core/azure-bulk-operations]].

## Before the scan

- **What is read** (since 2026-11-14): delete, resubmit and move call `CheckBeforeScanAsync` (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#CheckBeforeScanAsync`) before they create a receiver. It reads, through the administration client, the `MaxDeliveryCount` of the source only when the call reads its active sub-queue (a dead-letter queue has no delivery limit) and, for a resubmit or a move, `RequiresDuplicateDetection` of the target: the queue, or the parent topic of a subscription. A caller cancellation during the read propagates.
- **The refusals.** Every target is refused per sequence number, nothing received, sent or removed, with one of three fixed texts and no broker text: when the read fails, `SettingsUnreadable` ("The settings of the entity could not be read; the connection needs the Manage right for this. Nothing was sent or removed."); when the target detects duplicates and the request did not ask for new ids, `DuplicateDetectionRefusal` ("The target detects duplicates; a copy with the same message id would be dropped. Nothing was sent or removed.", `src/ServiceBusExplorer.Core.Tests/Providers/Azure/AzureServiceBusProviderBatchTests.cs#A_resubmit_or_move_into_a_target_that_detects_duplicates_refuses_every_message_and_receives_nothing`); when the max delivery count is 1, so one receive would dead-letter any unselected message, `DeliveryLimitNotReached` (the not-reached text below) (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#SettingsUnreadable`, `src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#DuplicateDetectionRefusal`, `src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#DeliveryLimitNotReached`).
- **Who needs Manage.** Owner decision of 2026-11-14: refuse only what is risky without Manage. A selective delete on a dead-letter or transfer dead-letter queue reads nothing, so a connection with Listen and Send but no Manage can run it (`src/ServiceBusExplorer.Core.Tests/Providers/Azure/AzureServiceBusProviderSubQueueTests.cs#A_dead_letter_delete_or_resubmit_never_reads_the_source_settings_so_a_connection_without_Manage_can_run_it`). A resubmit or a move still reads its target, and a delete or move on an active entity reads the source, so without Manage those are refused with the Manage text. A delete of all (`all: true`) reads `RequiresSession` before it drains, on a dead-letter queue too (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#PurgeEntityAsync`).
- **The single resubmit** (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#ResubmitDeadLetterMessageAsync`) runs the same check on its target before it peeks or sends, and turns a refusal into `InvalidEntityConfigurationException` with the fixed text, which the API answers as 400 ([[pages/services/api/routes-entities-and-messages]]). Its source is a dead-letter queue, so only the duplicate and the Manage texts can occur. Pinned by `src/ServiceBusExplorer.Core.Tests/Providers/Azure/AzureServiceBusProviderSubQueueTests.cs#A_single_resubmit_into_a_queue_or_topic_that_detects_duplicates_is_refused_with_the_fixed_text_and_sends_and_removes_nothing` and `src/ServiceBusExplorer.Core.Tests/Providers/Azure/AzureServiceBusProviderSubQueueTests.cs#A_single_resubmit_whose_target_settings_cannot_be_read_is_refused_with_the_Manage_text_and_no_broker_text`.

## New message ids

- **The flag** `newMessageIdOnDuplicateDetection`, default false, is on `ResubmitBatchRequest`, `MoveBatchRequest` and the optional body of the single resubmit (`src/ServiceBusExplorer.Core/Models/ResubmitMessageRequest.cs#NewMessageIdOnDuplicateDetection`). Into a target that detects duplicates, each copy gets a new `MessageId` and the first original id is kept in the application property `x-original-message-id` (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#OriginalMessageIdProperty`, `src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#GiveNewMessageId`); an existing value is never overwritten, so a second resubmit keeps the true original. Into a target without duplicate detection the flag changes nothing. RabbitMQ has no duplicate detection and ignores it.
- **The report.** A batch call maps each sequence number to its new id in `BatchOperationResult.NewMessageIds` (`src/ServiceBusExplorer.Core/Models/BatchOperationResult.cs#NewMessageIds`), only for a message that was handed to a send, so a message a failed send left unsent is never listed with one (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#SendResubmitBatchAsync`, `src/ServiceBusExplorer.Core.Tests/Providers/Azure/AzureServiceBusProviderBatchTests.cs#A_resubmit_or_move_with_new_ids_sends_each_copy_with_a_new_id_keeps_the_first_original_and_reports_it`). The single resubmit sends its copy with a new id and completes the source (`src/ServiceBusExplorer.Core.Tests/Providers/Azure/AzureServiceBusProviderSubQueueTests.cs#A_single_resubmit_with_a_new_id_into_a_target_that_detects_duplicates_sends_the_copy_with_a_new_id_keeps_the_original_and_completes_the_source`) but returns nothing, so the new id it used is not reported ([[pages/roadmap/followups]]).

## The delivery limit of an active entity

PeekLock counts a delivery on each receive, and the scan abandons what it does not select, so each unselected message it receives gets one more delivery; that cannot be avoided. `RecordReleases` (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#RecordReleases`) counts them in `UnselectedDeliveryCountRaised` and stops the delete or move scan after the cycle in which an unselected message's next delivery would reach `MaxDeliveryCount`; the targets left are reported "Not reached: going on would have sent unselected messages past their max delivery count into the dead-letter queue. Nothing was sent or removed." (`src/ServiceBusExplorer.Core.Tests/Providers/Azure/AzureServiceBusProviderBatchTests.cs#A_delete_or_move_on_an_active_entity_stops_before_receiving_again_an_unselected_message_at_its_limit_and_reports_the_rest_not_reached`). An unselected message received already at its last delivery is dead-lettered by its release; its sequence number is in `UnselectedDeadLettered`. Both fields are lower bounds: a message the receiver prefetched and never handed over is neither counted nor listed. The web app shows both in the results dialog ([[pages/services/web-app/bulk-new-message-id]]).
