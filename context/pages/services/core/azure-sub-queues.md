# Core: Azure sub-queues and scheduled messages

One topic of [[pages/services/core|Core]]; the map lists the others.

## Azure provider

**Sub-queues, scheduled messages and a disabled entity (2026-11-12).** One helper, `CreateReceiver`, builds the receiver of every message operation for a `MessageSubQueue` through the SDK's own sub-queue option (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#CreateReceiver`); no operation writes a path suffix by hand any more. The transfer dead-letter queue is declared by `SupportsTransferDeadLetter` (`src/ServiceBusExplorer.Core/Abstractions/IProviderCapabilities.cs#IProviderCapabilities`): true here, false for RabbitMQ, which refuses it on every operation (`src/ServiceBusExplorer.Core/Providers/RabbitMQ/RabbitMQProvider.cs#TransferDeadLetterNotSupported`). **Peek** no longer stops at the first short batch: it asks in batches of at most 250 from the last sequence number until a batch is empty or `count` is reached, at most `count` plus one broker calls (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#PeekCoreAsync`), so a scheduled message behind an active one is listed. Since 2026-11-13 `PeekMessagesAsync` takes an optional `fromSequenceNumber` before the token (`src/ServiceBusExplorer.Core/Abstractions/IMessagingProvider.cs#Task<IEnumerable<IMessage>> PeekMessagesAsync(string entityName, int count = 10,`): the first broker call asks from it instead of the head, in any sub-queue, and the same loop goes on from the last sequence number (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#PeekMessagesAsync`, `src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#PeekCoreAsync`); the session peeks start at the head. RabbitMQ throws `NotSupportedException` for any start, 0 included, before it checks the connection (`src/ServiceBusExplorer.Core/Providers/RabbitMQ/RabbitMQProvider.cs#PeekMessagesAsync`). An optional `includeBody`, true by default, sits between the start and the token (`src/ServiceBusExplorer.Core/Abstractions/IMessagingProvider.cs#Task<IEnumerable<IMessage>> PeekMessagesAsync(string entityName, int count = 10,`); false maps each message with a null body and does not decode it, every other field as with the body, size included, in both providers (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#MapToMessageInfo`, `src/ServiceBusExplorer.Core/Providers/RabbitMQ/RabbitMQProvider.cs#MapBasicGetToMessageInfo`). `IMessage.Body` is therefore `string?`; it is null only on such a peek. Peek and search check the caller's token before every broker call and hand it to the SDK (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#PeekCoreAsync`, `src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#SearchCoreAsync`). **Cancel of scheduled messages,** of a queue or a topic (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#CancelScheduledMessagesAsync`): 1 to 500 positive distinct sequence numbers, validated before any broker call (`src/ServiceBusExplorer.Core/Providers/Azure/EntityConfigurationValidator.cs#ValidateScheduledSequenceNumbers`); one broker call when all are scheduled, one call per number only after the broker reports one not found (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#CancelEachScheduledAsync`), at most 501 calls; a failed number carries one of three fixed sentences (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#EntityDisabledError` to `src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#CancelFailedError`) and the causes are logged in one warning per request (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#CancelScheduledCoreAsync`). RabbitMQ refuses it (`src/ServiceBusExplorer.Core/Providers/RabbitMQ/RabbitMQProvider.cs#CancelScheduledMessagesAsync`). **A disabled entity** becomes the neutral `EntityDisabledException` (`src/ServiceBusExplorer.Core/Abstractions/EntityAdministrationExceptions.cs#EntityDisabledException`) on every message path (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#RefuseDisabledAsync`); in a bulk operation that already started, the remaining sequence numbers are failures with the text "The entity is disabled for this operation." and nothing is retried (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#DeleteMessagesCoreAsync`, `src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#ResubmitCoreAsync`, `src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#MoveCoreAsync`, `src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#CancelEachScheduledAsync`). The exception guarantees only that no message was removed from its source; the limit is on [[pages/invariants/bulk-operations-are-at-least-once]]. A deferred message is listed with its state; since 2026-11-14 it can be deleted, resubmitted or dead-lettered by its sequence number ([[pages/services/core/azure-deferred]]).

**Scheduled messages of a topic (2026-11-14).** `CancelScheduledMessagesAsync` takes a queue or a topic name: the sender is created on the entity named, and a scheduled message sent to a topic stays in the topic until it is due, so it is cancelled there, with the same bound, per-number result and fixed sentences (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#CancelScheduledMessagesAsync`). `SendMessageAsync` now returns `long?`: a request with `ScheduledEnqueueTime` goes through `ServiceBusSender.ScheduleMessageAsync`, the only send that answers the sequence number, and a send without a time returns null; RabbitMQ returns null (`src/ServiceBusExplorer.Core/Abstractions/IMessagingProvider.cs#SendMessageAsync`). On the emulator a peek on the topic path returns its scheduled messages (`src/ServiceBusExplorer.IntegrationTests/AzureServiceBusProviderTests.cs#On_the_emulator_a_peek_on_the_topic_path_returns_its_scheduled_messages`); real Azure was not verified and no route lists them yet ([[pages/roadmap/followups]]). A topic message cancelled by the returned number never reaches its subscription (`src/ServiceBusExplorer.IntegrationTests/AzureServiceBusProviderTests.cs#A_message_scheduled_on_a_topic_and_cancelled_by_the_returned_sequence_number_never_reaches_the_subscription`).
