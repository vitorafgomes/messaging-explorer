# Api: Entity and message routes

One topic of [[pages/services/api|Api]]; the map lists the others.

## Controllers

**Entity administration (2026-11-12).** `POST` on queues, topics and subscriptions takes `{ name, options }` with typed fields and no dictionary (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#GetQueue`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#GetTopic`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#GetSubscription`); `PATCH` on each edits only the fields sent and returns the entity read again (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#CreateQueue`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#CreateTopic`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#CreateSubscription`). The controllers know no limit: the provider validates. They map the provider's neutral exceptions to 409 already exists, 404 not found and 400 invalid configuration, a provider that cannot update to 400, anything else to the constant 500 body (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#Failure`). A response never carries the broker's text and a log line never carries the request body.

**Sub-queues, scheduled messages and a disabled entity (2026-11-12).** The active, dead-letter and transfer dead-letter routes of an operation are one-line actions over one private action that takes a `MessageSubQueue` (for example `src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Search`, `src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Peek`). Eight routes read the transfer dead-letter queue, four for a queue and four for a subscription, mirroring the dead-letter peek, search, delete-batch and resubmit-batch (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#PeekDeadLetterMessages`, `src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#SearchDeadLetterMessages`, `src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#DeleteDeadLetterMessages`, `src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#ResubmitDeadLetterMessages`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#PeekDeadLetterMessages`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#SearchSubscriptionDeadLetterMessages`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#DeleteDeadLetterMessages`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#ResubmitDeadLetterMessages`); a provider without `SupportsTransferDeadLetter` answers 400 and is never called (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#SubQueueNotSupported`), there is no purge and no move for it, and its delete-batch refuses `all: true` with 400 (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#DeleteBatch`, `src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#DeleteAllOfTransferDeadLetter`). `POST api/queues/{name}/messages/cancel-scheduled` takes `{ sequenceNumbers }` (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#ReceiveMessages`), answers the result in the delete-batch shape, 400 with the provider's own text when it refuses the numbers (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#CancelScheduledMessages`) and 400 for a provider without scheduled messages (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#ScheduledMessagesNotSupported`); queues only. A disabled entity answers 409 `{ "message": "The entity is disabled for this operation." }` on every message route (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#EntityDisabled`), where it answered the constant 500. Peek and search hand the provider the request token (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Peek`, `src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Search`), and the capabilities answer carries `supportsTransferDeadLetter` (`src/ServiceBusExplorer.Api/Controllers/ConnectionsController.cs#GetProviderCapabilities`). Pinned by `src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs`: each transfer route against its dead-letter sibling (`:51`), `all: true` refused (`:82`), the token (`:98`, `:107`), the unsupported provider (`:123`, `:165`), the cancel result and its 400 (`:133`, `:154`), the 409 on every message route (`:207`) and the API key on the new routes (`:243`).

**Peek from a position (2026-11-13).** The four dead-letter and transfer dead-letter peek routes, of a queue and of a subscription, take an optional `fromSequenceNumber` (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#PeekDeadLetterMessages`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#PeekDeadLetterMessages`); the active peek does not. It is bound as text and read as a whole number of 0 or more, digits only (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#PeekPosition`): a sign, a space, a decimal, an exponent or a value past `long` answers 400 `{ "message": "fromSequenceNumber must be a whole number of 0 or more." }`, never the framework's validation body, and the provider is not called. An empty value (`?fromSequenceNumber=`) counts as absent. A provider without `SupportsPeekFromSequenceNumber` answers 400 `{ "message": "This provider cannot read the dead-letter queue from a position." }` when the parameter is present and is never called (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#PeekPosition`); the check runs before the transfer dead-letter check, so RabbitMQ gives that text on all four routes (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Peek`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#Peek`). Otherwise the value reaches the provider's peek with the clamped count and the request token, and the answer is the messages from that sequence number on, in order ([[pages/services/core]]). Absent, a route answers as before. A failing peek from a position answers what a failing peek from the head answers, the constant 500. The capabilities answer carries `supportsPeekFromSequenceNumber` (`src/ServiceBusExplorer.Api/Controllers/ConnectionsController.cs#GetProviderCapabilities`). Pinned by `src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs`: the pass-through on the four routes and position 0 (`src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#A_dead_letter_peek_with_fromSequenceNumber_hands_the_provider_that_position_with_the_count_and_the_sub_queue`, `src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#A_dead_letter_peek_from_position_0_reads_from_sequence_number_0`), the absent and empty value (`src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#A_dead_letter_peek_without_fromSequenceNumber_reads_from_the_head_as_before`), the refused values (`src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#A_dead_letter_peek_whose_fromSequenceNumber_is_not_a_whole_number_of_0_or_more_answers_400_naming_the_field_and_is_never_called`), the provider without the capability with and without the parameter (`src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#A_provider_that_cannot_read_from_a_position_answers_400_with_that_text_to_a_dead_letter_peek_with_fromSequenceNumber_and_is_never_called`, `src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#A_provider_that_cannot_read_from_a_position_still_peeks_the_dead_letter_queue_from_the_head`), the failing call (`src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#A_dead_letter_peek_from_a_position_that_fails_answers_the_same_constant_500_as_a_failed_peek_from_the_head`), the capability (`src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#The_capabilities_say_whether_the_provider_can_peek_from_a_sequence_number`) and the API key (`src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#A_dead_letter_peek_with_fromSequenceNumber_without_the_api_key_is_refused_with_401`).

**Peek without bodies (2026-11-13).** The same four routes take an optional `includeBody`, true when absent or empty. `false` answers each message with `"body": null` and every other field as read, size included; the run of the automatic resubmit reads only the sequence number, the enqueued time, the reason and the subject, so it no longer copies every body of the queue over loopback. Only the literals `true` and `false` are accepted: anything else, `False` or `1` included, answers 400 `{ "message": "includeBody must be true or false." }` and the provider is not called (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#IncludeBody`, `src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Peek`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#Peek`). The value reaches the provider's peek ([[pages/services/core]]); the active peek always asks for bodies. Pinned by `src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#A_dead_letter_peek_with_includeBody_false_asks_the_provider_for_no_bodies_and_answers_body_null` (four routes, `false` reaching the provider and `body` null in the JSON), `:421` (true, absent, empty and the active peek ask for bodies) and `:437` (the refused values).
