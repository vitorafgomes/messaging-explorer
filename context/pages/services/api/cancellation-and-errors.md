# Api: Cancellation and error mapping

One topic of [[pages/services/api|Api]]; the map lists the others.

## Controllers

### Cancellation

The bulk and destructive actions pass `HttpContext.RequestAborted` to the provider: purge (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Purge`), delete-batch (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#DeleteBatch`), move-batch (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#MoveBatch`), resubmit-batch (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#ResubmitBatch`) and cancel-scheduled (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#CancelScheduledMessages`), and the same four under a subscription (`src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#Purge`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#DeleteBatch`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#MoveBatch`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#ResubmitBatch`). A client abort therefore cancels the Core loop between batches ([[pages/invariants/bulk-operations-are-at-least-once]]: messages already moved or completed before the abort stay done). Since 2026-11-12 peek and search pass it too (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Peek`, `src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Search`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#Peek`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#Search`). Not cancellable from the request: receive (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#ReceiveMessages`), send, single resubmit (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#ResubmitDeadLetterMessage`) and entity create/delete. `MetricsController` and the `counts` route of `MonitoringController` model-bind a `CancellationToken` parameter (`src/ServiceBusExplorer.Api/Controllers/MetricsController.cs#GetQueueMetrics`, `src/ServiceBusExplorer.Api/Controllers/MonitoringController.cs#GetCounts`).

The session routes treat a read the caller abandoned as no error: when `RequestAborted` fired, an `OperationCanceledException` ends the request with no body and no log (`src/ServiceBusExplorer.Api/Controllers/SessionsController.cs#Run`), so the web app's List again, a change of entity or its 10-second cut on the session accepts writes nothing to the log. Pinned by `src/ServiceBusExplorer.Api.Tests/SessionCancelTests.cs#A_session_read_the_caller_abandons_reaches_the_provider_cancelled_and_logs_no_error`, which saw an error entry before the change. The namespace properties read does the same (`src/ServiceBusExplorer.Api/Controllers/NamespaceController.cs#Properties`), pinned by `src/ServiceBusExplorer.Api.Tests/SessionCancelTests.cs#A_namespace_properties_read_the_caller_abandons_reaches_the_provider_cancelled_and_logs_no_error`: without the filtered catch it logs "Read of the namespace properties failed". An accept abandoned at any moment leaves the session acceptable at once on the emulator (`src/ServiceBusExplorer.IntegrationTests/AzureServiceBusSessionTests.cs#A_session_read_the_caller_abandons_at_any_moment_leaves_the_session_acceptable_at_once`).

### Error mapping

Two layers, one body. One exception since 2026-11-19: an operation the broker refuses as not authorised answers 502 with a fixed sentence naming the rights it needs, from every catch and from the handler (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#Unhandled`); a refusal of the file system stays the 500 (`src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#A_file_this_user_may_not_open_and_a_refusal_buried_deeper_than_five_errors_stay_the_constant_500`). Most actions catch `Exception`, log it and return a constant 500; an exception no action catches reaches the exception handler, the outermost middleware (`src/ServiceBusExplorer.Api/Program.cs#FileWorkspaceManager`), which answers the same 500 `{message:"An internal error occurred."}` as JSON in every environment, Development included. The framework's `ExceptionHandlerMiddleware` logs that exception once at Error; the handler logs nothing itself, and no exception text reaches the client.

- One 500 adds a fixed reason: a connect whose failure is a refused port, a host not found, a timeout or a failed TLS handshake answers `{message, code}` with a fixed sentence and code (`src/ServiceBusExplorer.Api/Controllers/ConnectionsController.cs#ConnectFailureReason`), never the exception text, which can carry the connection string, the user name or the password. Pinned by `src/ServiceBusExplorer.Api.Tests/ConnectFailureReasonTests.cs`, a sentinel key and user name in the failure and the stored connection.
- Every other 500 body is `{message:"An internal error occurred."}`: Queues/Topics/Sessions (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Search`), Connections/Groups (`src/ServiceBusExplorer.Api/Controllers/ConnectionsController.cs#GetConnections`) and the handler. Pinned by `src/ServiceBusExplorer.Api.Tests/ErrorBodyTests.cs#A_caught_provider_failure_answers_500_with_the_message_key` for one caught failure in each of Queues, Topics and Sessions, and by `src/ServiceBusExplorer.Api.Tests/ErrorBodyTests.cs#An_unhandled_exception_answers_a_constant_500_body_and_never_the_exception_text` for the handler under Development and Production.
- Metrics: 503 `{message, configurationRequired:true}` when the exception text contains "not properly configured" (`src/ServiceBusExplorer.Api/Controllers/MetricsController.cs#GetQueueMetrics`), else 500 `{message:"Failed to fetch queue metrics."}` (`:58`).
- Sessions map their refusals to 400, 404 and two 409s with a `code` (see Sessions on [[pages/services/api/routes-sessions-and-definitions]]); `SessionsController` and `Capabilities` clamp or reject inputs (`src/ServiceBusExplorer.Api/Controllers/SessionsController.cs#List`, `src/ServiceBusExplorer.Api/Controllers/ConnectionsController.cs#GetProviderCapabilities`).
- A disabled entity is not a 500: every message route catches `EntityDisabledException` and answers 409 with the fixed text (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#EntityDisabled`, for example `src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Search`).
- Counts are clamped to 1..1000 on peek (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Peek`) and receive (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#ReceiveMessages`) and monitoring history to 1..120 (`src/ServiceBusExplorer.Api/Controllers/MonitoringController.cs#GetHistory`).
- No controller returns the text of a broker or framework exception. An `InvalidEntityConfigurationException`, whose message is the application's own fixed text, answers 400 with it: the cancel of scheduled messages, the single resubmit's refusal and the deferred batches (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#DeferredBatch`). The single send answers it the same way (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#SendMessage`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#SendMessage`). The purge routes answer it the same way, and the search routes answer a fixed 400 where the provider declares it cannot search (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#SearchNotSupported`, `src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#A_provider_that_cannot_search_messages_answers_400_and_is_never_called_instead_of_an_empty_result`). A `MessageReadFailedException`, whose message is likewise the application's own, answers 502 with it on a peek and on a receive (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#ReadFailed`). `ImportConfiguration` answers an `ArgumentException` with 400 and the constant `{message:"Invalid or empty configuration data"}` (`src/ServiceBusExplorer.Api/Controllers/ConnectionsController.cs#ImportConfiguration`): the two `ArgumentException`s Core throws there carry literal text, but the catch also takes any framework `ArgumentException`, which the action cannot tell apart, so it never echoes `ex.Message`. Pinned by `src/ServiceBusExplorer.Api.Tests/ErrorBodyTests.cs#Import_never_returns_the_message_of_an_argument_exception`. `TestConnection` returns 200 with `success:false` and an `error` text it builds itself rather than an error status (`:223`); that 200 body is not a 500 and keeps its `error` key, which the add-connection dialog reads.
- Counts are clamped to 1..1000 on peek (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Peek`) and receive (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#ReceiveMessages`) and monitoring history to 1..120 (`src/ServiceBusExplorer.Api/Controllers/MonitoringController.cs#GetHistory`).
- A peek the broker did not answer is not a 500 either: the two peek helpers catch `MessageReadFailedException` and answer 502 with its message, a fixed sentence and the name of the provider's failure reason in brackets; the broker's own error is logged as a warning and never answered (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#ReadFailed`, `src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#Peek`, `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#Peek`). Any other failure of a peek still reaches the exception handler.
- Actions that catch no general failure reach the exception handler and answer the constant 500: the reads (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#GetQueues`, all `GetX`), entity delete, and send, batch send and receive, which catch only the disabled entity and, for the single send, a refusal (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#SendMessage`, `src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#SendMessages`, `src/ServiceBusExplorer.Api/Controllers/QueuesController.cs#ReceiveMessages`, topic send `src/ServiceBusExplorer.Api/Controllers/TopicsController.cs#DeleteTopic`).
