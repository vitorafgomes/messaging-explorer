# Web App: Entity administration, sub-queues and sessions

One topic of [[pages/services/web-app|Web App]]; the map lists the others.

## features/

**Entity administration (2026-11-12),** under `features/entities/`: `entity-form-dialog` (create and edit of a queue, topic or subscription), `entity-review-dialog` (the changed fields with current and new value, before saving), `entity-status-dialog` (a status other than Active needs the entity's name typed) and `entity-admin-actions` (the status chip and the Edit and Status actions of the panel header). Angular Material, each with a spec. They appear only when the API's own answer says `supportsEntityUpdate` is true; unlike the other capabilities, a default never turns this one on, nor the rules editor, nor the transfer dead-letter queue (`web-app/src/app/core/services/provider.service.ts#unconfirmed`). `ApiService` gained `patch` (`web-app/src/app/core/services/api.service.ts#patch`); durations go to the wire through one formatter (`web-app/src/app/features/entities/duration.ts#toTimeSpan`) and the contract's limits are mirrored in `entity-validation.ts` for inline errors, the server being the authority. A duration's unit select shows "Unit" and is named "Unit of {label}"; the summary of changes in an edit is a section named "Summary of changes" (`web-app/src/app/features/entities/entity-form-dialog.component.html`).

**Sub-queues, scheduled messages and a disabled entity (2026-11-12),** under `features/messages/`. The messages dialog no longer carries a dead-letter boolean: one `subQueue` value is derived from the tab shown (`web-app/src/app/features/messages/view-messages-dialog.component.ts#isAllActiveSelected`) and every list, selection and action reads it. A third tab, Transfer dead-letter, appears only when the API's own answer says `supportsTransferDeadLetter` is true (`web-app/src/app/features/messages/view-messages-dialog.component.ts#MAX_CANCEL_SCHEDULED`); it peeks, searches, deletes a selection and resubmits (`web-app/src/app/core/services/queue.service.ts#peekTransferDeadLetterMessages`, `web-app/src/app/core/services/topic.service.ts#peekTransferDeadLetterMessages`), with no purge and no move. The queue and subscription panels show a Transfer Dead Letter card, at 0 too since 2026-11-15, whenever the API declares supportsAutoForwarding, and it opens that tab only under the same flag (`web-app/src/app/features/entities/entity-details.component.ts#supportsAutoForwarding`, `web-app/src/app/features/entities/entity-details.component.ts#transferDeadLetterReachable`). Each message shows a state chip when it is Scheduled or Deferred (`web-app/src/app/features/messages/view-messages-dialog.component.ts#</div>`); a "Scheduled" filter on a queue's Active tab narrows the loaded messages, client side (`web-app/src/app/features/messages/view-messages-dialog.component.ts#getRegexError`). Cancel scheduled is offered on a queue's Active tab only (`web-app/src/app/features/messages/view-messages-dialog.component.ts#resultsDialogRef`) and enabled only when every selected message is scheduled and at most 500 are selected (`web-app/src/app/features/messages/view-messages-dialog.component.ts#resultsDialogRef`, `web-app/src/app/features/messages/view-messages-dialog.component.ts`); `cancel-scheduled-dialog` confirms it and needs the queue name typed for more than one message (`web-app/src/app/features/messages/cancel-scheduled-dialog.component.ts#CancelScheduledDialogComponent`); the result opens in the bulk results dialog. A 409 from any message call is shown in the API's own words, "The entity is disabled for this operation." (`web-app/src/app/features/messages/message-call-failure.ts#messageCallFailure`). `supportsDeferral` defaults to false. Paging past the first read, Load more from the last sequence number + 1, and the deferred actions: [[pages/services/web-app/bulk-deferred-messages]]. Open points are on [[pages/roadmap/followups]].

**The states, header and detail of the messages dialog.** A first load that fails shows, in place of the list, an error with Retry, or for a 409 "The entity is disabled for this operation." with Load again; no message is shown, as none was read. A refresh that fails with a list on screen keeps the list and the selection and says why in a snack bar, so a retry never loses a selection (`web-app/src/app/features/messages/view-messages-dialog.component.ts#loadFailed`). An empty tab, Active, Dead Letter or Transfer dead-letter, says under an h2 title the broker answered with none and the count asked for, with Send a message and Refresh of that tab. The header has Send, which opens the send dialog on the queue or on the topic of a subscription and reloads the active messages after a send (`web-app/src/app/features/messages/view-messages-dialog.component.ts#sendMessage`), and Close. The detail has its own close button, Copy body, a "Why it was dead-lettered" block on the dead-letter and transfer dead-letter tabs, and the deferred note as a note. The search's regex toggle is named "Regular expression". While a tab loads, six skeleton rows sit under the loading line, hidden from a screen reader. The list is a `ul` whose `li` rows hold a checkbox and a button that opens the row, with `aria-current` on the opened one. A filtered tab says "Showing X of Y messages" at the end of its Select All row (`web-app/src/app/features/messages/view-messages-dialog.component.ts#filterSummary`). The no-match state holds its icon, the h2 "No messages match your filter" and the only Clear all, on all three tabs and also when Show = Scheduled leaves nothing; Clear all of the Active tab sets Show back to All (`web-app/src/app/features/messages/view-messages-dialog.component.ts#clearAllActiveFilters`). Send a message carries the send icon; the disabled panel is a section named "Entity disabled". Pinned by `web-app/src/app/features/messages/view-messages-dialog.component.spec.ts#the dialog as the Messages artboard draws it`.

**The send dialog** shows the body, the properties and the delivery options with the custom properties as three columns on one page, wider than before (1100 px, at most 95% of the window). Saving a template asks its name and deleting one asks to confirm on the dialog itself, never in a browser prompt or confirm (`web-app/src/app/features/messages/send-message-dialog.component.ts#confirmSaveTemplate`); Format JSON says Invalid JSON beside it; the schedule and time to live say what empty means; Send says why it is off with no body; an edited resubmit names the dead-letter message it was filled from (`web-app/src/app/features/messages/send-message-dialog.component.ts#sourceSequenceNumber`). The diff's section list is named "What to compare" (`web-app/src/app/features/messages/message-diff-dialog.component.ts#MessageDiffDialogComponent`). A sent import says "Import complete: N sent successfully" in a snack bar with Close, and the dialog keeps no success note; a refused import stays in the dialog as an error with the count that failed, and its reason goes in a snack bar (`web-app/src/app/features/messages/import-messages-dialog.component.ts#importMessages`). The move, import and export dialogs each have a spec of the words Send.dc.html draws.

**Sessions (2026-11-13),** under `features/entities/`: `entity-sessions` serves the queue panel and the subscription panel alike. The queue panel gained Material tabs, Properties and Sessions (`web-app/src/app/features/entities/entity-details.component.ts#NOT_SET`); the subscription has a Material tab bar over panels it hides and shows, Description, Sessions and Rules, and mounts the same component (`web-app/src/app/features/entities/entity-details.component.ts#<mat-tab-nav-panel #subscriptionPanel>`). Either appears only when the entity requires sessions and the capability is not explicitly false. The component is created the first time its tab opens, so selecting an entity reads nothing, and is then kept while that entity stays selected: the queue's tab group preserves its content and the subscription hides the component instead of destroying it, so going back to the tab shows the same list without a second scan. Another entity, or a reload of the selection (after a purge, say), drops it until the tab opens again (`web-app/src/app/features/entities/entity-details.component.ts#key`). `SessionService` calls the three routes under `api/queues/{name}/sessions` and `api/topics/{topic}/subscriptions/{subscription}/sessions` through one path helper (`web-app/src/app/core/services/session.service.ts#list`); the old `api/sessions` routes and their callers are gone.
- **The list is a passive scan, then one accept per listed session.** The notice says, as drawn, that listing locks each session briefly, and it is on screen before the first accept. The scan (`GET .../sessions`, at most 100 sessions) gives the ids; each id is then accepted once with `messageCount=0`, at most four at a time (`web-app/src/app/features/entities/entity-sessions.component.ts#LOCK_CONCURRENCY`) and for at most 10 seconds (`web-app/src/app/features/entities/entity-sessions.component.ts#LISTING_LIMIT_MS`), only when the tab opens or on List again (`web-app/src/app/features/entities/entity-sessions.component.ts#readLocks`); destroying it is pinned by `web-app/src/app/features/entities/entity-sessions.component.spec.ts#destroying the tab cancels the accepts still in flight and asks for no more`. The table shows Session ID, Lock Status and State; a 409 with code `SessionInUse` is Locked, any other failure shows "Not read" with its reason, never Unlocked or No state (`web-app/src/app/features/entities/entity-sessions.component.ts#inUse`); a session not read in 10 seconds stays listed as not read. List again, another entity or destroying the component cancels the accepts in flight (switching to another tab of the panel keeps it, and the accepts, alive), and the aborted request releases the accept on the server. Opening a session by its id stays below the table, for a session that holds only a state.
- **Opening one session is one request:** `GET .../sessions/{sessionId}?messageCount=100` (`web-app/src/app/features/entities/entity-sessions.component.ts#open`). The facts show Session ID and Lock Status; then "Session State" with the state or "No state data"; then "Messages of this session" with Sequence, Message ID, Enqueued (UTC) and Size (the body's bytes, as the API maps it), and the footnote "Peeked, not received". Another receiver's lock expiry is not known, so Locked carries no time.
- **The state is edited inline and written only after a confirmation that never overwrites a changed state.** Edit state opens "New state" with its hint, Cancel and Review change, disabled with the drawn title while the text equals the state as read, and past 262144 UTF-8 bytes (`web-app/src/app/features/entities/entity-sessions.component.ts#review`). The confirmation, `session-state-dialog`, shows the drawn consequence, the facts Session ID, the entity, Connection and Environment, and the current and new state with "No state data" for none; the write carries `expectedState` exactly as read on opening (`web-app/src/app/features/entities/session-state-dialog.component.ts#write`). On `SessionStateChanged` it disables the write and offers Reload, and Back closes it as stale so nothing is sent again (`web-app/src/app/features/entities/session-state-dialog.component.ts#back`).
