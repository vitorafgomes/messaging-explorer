# Web App: Settings and the feature folders

One topic of [[pages/services/web-app|Web App]]; the map lists the others.

## features/

**Settings (2026-11-13),** under `features/settings/`, drawn from the artboard `context/prototypes/web-app/Settings.dc.html`: five sections, Material components and theme tokens only (`web-app/src/app/features/settings/settings.component.html`).
- **Appearance.** System, Light and Dark on `ThemeService`, remembered under `app-theme`; System follows the `prefers-color-scheme` setting of the computer as it changes (`web-app/src/app/core/services/theme.service.ts#setMode`). The toolbar button stays, and sets Light or Dark.
- **Updates.** `AppUpdateService` (`web-app/src/app/features/settings/app-update.service.ts#AppUpdateService`), a root service started by `App` under Electron, holds what the toolbar badge and the update buttons of `App` held: the version, the channel, the status, the version offered, the percent and the updater's reason. It registers the one `onUpdateStatus` listener, so the screen shows events that arrived before it opened. Its states are distinct: unavailable (no Electron: "Updates are handled by the desktop app", the release page only), not checked yet, checking, a development build (the `dev-mode` answer of the shell), up to date, available with Download, downloading with the percent, ready with Restart to Update, and failed, where a failure after Download reads "was not downloaded" and one after a check "Could not check", each with the reason, Retry and the release page (`web-app/src/app/features/settings/app-update.service.ts#check`). A check the shell answers without any event ends as a failed check, never a spinner. Last check shows the time a check answered (up to date, available, a failed check, a development build), or "Not in this session". An available version lists its release notes, which the shell sends with the event, as plain lines: the HTML is parsed into an inert document and only its text is shown (`web-app/src/app/features/settings/app-update.service.ts#releaseNoteLines`). The panels take the status tokens of `web-app/src/styles.scss`: up to date and ready the success colours, a package that cannot update itself the warning container. The channel is a Stable and Beta toggle; it changes only when `setUpdateChannel` answers ok, and is then checked again (`web-app/src/app/features/settings/app-update.service.ts#setChannel`).
- **A package that can update itself** downloads a found version on its own; the available state says so and Download starts it at once. A failed download is reported as a download whether the user or the shell started it (`web-app/src/app/features/settings/app-update.service.spec.ts#a download the shell started on its own that fails is reported as a download, not as a check`).
- **A package that cannot update itself.** The shell's `getSelfUpdateBlocker` says why ([[pages/services/electron-shell]]). With a reason, the available, downloading and ready states are replaced by "Version N is available, and this package cannot update itself", the reason for this platform and "Open the download page", which opens the release of that version (`web-app/src/app/features/settings/settings.component.html#@if (blockerReason(); as blocked) {`); the service never calls download or install then (`web-app/src/app/features/settings/app-update.service.ts#download`). Links to the releases page are anchors with `target="_blank"`, so the shell's window-open handler sends them to the browser through `isSafeExternalUrl`.
- **The toolbar** lost the version badge and its channel menu; it keeps one compact link while an update is available, downloading, ready or failed, which opens Settings and never downloads or installs itself (`web-app/src/app/app.html#@switch (updates.status()) {`), and the download bar under it.
- **Data.** The real path of the file in monospace, asked of the shell (`web-app/src/app/features/settings/settings.component.ts#dataFile`), with Show in folder, which shows it in the file manager and says why when it cannot (`web-app/src/app/features/settings/settings.component.ts#showDataFile`); neither outside the desktop app. The sentence that it holds the secrets in plain text, Move connections with Export and Import, which open the Connections screen, then a danger zone with Clear all data. `clear-all-data-dialog` reads the connections and the groups when it opens and names them, the file `data/workspace.json`, that no broker is touched and, when connected, the connection the app leaves first; it names clients and environments apart, offers to export the connections first, and shows the words as a placeholder; Clear stays disabled until "clear all data" is typed, compared after trimming, case included, and while the counts are loading or failed (`web-app/src/app/features/settings/clear-all-data-dialog.component.ts#ClearAllDataDialogComponent`). It calls the existing `DELETE connections/clear-all` through `ConnectionService`; after a clear the screen reads the connection status again, because the API disconnected and the clear answers counts, not a status; a failure keeps the dialog open and says the data was not cleared. The button of the connections debug panel is gone.
- **Developer.** A checkbox on `DevSettingsService`, the same state as Ctrl+Shift+D. In the desktop app, in every build, Developer tools has "Open developer tools" (`web-app/src/app/features/settings/settings.component.ts#openDevTools`) and the drawn warning that the tools show every request to the local API with its key; outside the desktop app the row is absent (`web-app/src/app/features/settings/settings.component.ts#canOpenDevTools`).
- **About.** Name, version and channel, licence and what it is built with, as the artboard draws them; the API port and key appear nowhere on the screen; Repository, Changelog and Report a security problem privately, a GitHub private advisory, as links to the browser; and Report a bug and Suggest a feature, which open the existing bug report through `BugReportService` (`web-app/src/app/shared/bug-report.service.ts#open`), the same as the Help menu, errors included. The dialog says nothing is sent from the app, previews the issue body exactly as Submit posts it (`web-app/src/app/shared/bug-report-dialog.component.ts#issueBody`), and says the name is published and the issue public; pinned by `web-app/src/app/shared/bug-report-dialog.component.spec.ts`.
- Pinned by `web-app/src/app/features/settings/settings.component.spec.ts`, `web-app/src/app/features/settings/app-update.service.spec.ts`, `web-app/src/app/features/settings/clear-all-data-dialog.component.spec.ts`, `web-app/src/app/features/connections/connections-debug-panel.spec.ts` and the end-to-end flow `web-app/e2e/settings.e2e.ts`.
- Not built from the artboard: the reasons of every platform as a list, where the screen names this platform's only; the environment chip of the clear dialog (lane L5); nothing else of the two dialogs. The caption under the preview says "No connection, no namespace, no message body.", which holds because every caught error is kept with its addresses and host names taken out (`web-app/src/app/shared/bug-report.service.ts#redact`).

- `connections/` - the connection list, the add and edit dialog, clients and environments, export and import: [[pages/services/web-app/features-connections]].
- `entities/` - the main workspace: tree plus details (`web-app/src/app/features/entities/entities-container.component.ts`), transfer monitor. The metrics dashboard that drew mock data was removed on 2026-11-12.
- `messages/` - view, send, import, export, move, diff and continuous-resubmit dialogs.
- `queues/`, `topics/` - list pages with per-row actions. Since 2026-11-13 both are Material and theme tokens: the queues are a `mat-table`, the topics a list of disclosure buttons that load the subscriptions of a topic on open (`web-app/src/app/features/topics/topics.component.ts#toggleTopic`). A count opens the messages of its sub-queue; View and Send are named icon buttons; the two purges are in a menu named "More actions for {name}", in the error colour, each disabled at a count of 0, and ask the same confirmation as before. Loading, empty and a failed load are three states; a failed load of the list says it could not be read and offers Retry, where it used to end on "No queues found" or "No topics found" behind a snackbar (`web-app/src/app/features/queues/queues.component.ts#loadError`, `web-app/src/app/features/topics/topics.component.ts#loadError`). Pinned by `web-app/src/app/features/queues/queues.component.spec.ts` and `web-app/src/app/features/topics/topics.component.spec.ts#a topic list the API fails to return is an error with Retry, never "No topics found"; Retry asks again and shows the topics`.
- `monitoring/` - snapshot and history trend (`web-app/src/app/features/monitoring/monitoring.component.ts#MonitoringComponent`) and, since 2026-11-13, the counts of every entity ([[pages/services/web-app/features-monitoring]]).
