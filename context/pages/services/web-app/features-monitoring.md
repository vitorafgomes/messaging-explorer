# Web App: Monitoring screen

One topic of [[pages/services/web-app|Web App]]; the map lists the others.

## features/

**Monitoring (2026-11-13).** The screen reads `GET monitoring/snapshot`, now `{ snapshot, pollIntervalSeconds, lastPollFailedAt }`, with the recent history when it opens or the connection changes, and the snapshot again every 30 seconds from the local API (`web-app/src/app/features/monitoring/monitoring.component.ts#load`). Its states are distinct: loading until the API answers; "Waiting for the API's first poll of the broker" while `snapshot` is null and no poll failed; "Could not read the counts from the broker", with the time and Retry, while `snapshot` is null and a poll failed; "Could not load the monitoring data" when the request itself fails; "Nothing to monitor in this namespace" only for a snapshot with no entity; and over data from before a failed poll, a line saying the last poll failed and when the counts are from. The header says how often the API reads the broker. Two Material tabs follow: Overview and All entities, `monitoring-counts` (`web-app/src/app/features/monitoring/monitoring-counts.component.ts#MonitoringCountsComponent`), drawn from the `counts` state of the monitoring artboard:
- one `mat-table` of every queue and subscription with Name (a subscription says its topic), Kind, Active, Dead-letter, Scheduled and Transfer dead-letter; a count the API sends as null reads "Not counted", which is every subscription's scheduled count;
- `matSort` on every column, dead-letter descending at first, a text column ascending on its first click and a count descending, a null count sorting below zero (`web-app/src/app/features/monitoring/monitoring-counts.component.ts#over`);
- a name filter that matches part of the name or of the topic, ignoring case, with a line saying how many entities match and how many are over the threshold (`web-app/src/app/features/monitoring/monitoring-counts.component.ts#over`);
- a dead-letter threshold, a whole number, 100 at first, kept in `localStorage` under `monitoring-dead-letter-threshold` (`web-app/src/app/features/monitoring/monitoring-counts.component.ts#onThreshold`); a row whose dead-letter count is strictly above it is marked "over threshold" in the warning container colour;
- the name, a button named "Open {name} in Entities", selects that queue, or that subscription of its topic, in `EntitySelectionService` and navigates to `/entities` (`web-app/src/app/features/monitoring/monitoring-counts.component.ts#open`);
- "Auto resubmit" on each row whose dead-letter count is above zero, named "Auto resubmit the {n} dead-letter messages of {name}", unless the provider says it has no dead-letter queue (`web-app/src/app/features/monitoring/monitoring-counts.component.ts#canResubmit`); it opens the auto resubmit dialog of that queue or subscription (`web-app/src/app/features/monitoring/monitoring-counts.component.ts#autoResubmit`). The per-row refresh is gone; `GET monitoring/counts` has no caller in the app now;
- "Refresh every" 30 seconds, 1 minute or 5 minutes, "30 seconds is the floor." (`web-app/src/app/features/monitoring/monitoring-counts.component.ts#REFRESH_PERIODS`), handed to the screen, which polls at that period and never below 30 seconds (`web-app/src/app/features/monitoring/monitoring-counts.component.ts#refreshSeconds`).
**Header and states (2026-11-14).** The header names the connected namespace above the title "Monitoring" (`web-app/src/app/features/monitoring/monitoring.component.ts#host`); "Last update HH:mm:ss." and Refresh show only over counts that were read, and on the Overview the note adds "Refreshes every {period}.". Loading names the namespace over four card blocks and three lines; empty says the namespace answered and holds no queue and no subscription, with "Create one in Entities". The screen waits 30 seconds for the API (`web-app/src/app/features/monitoring/monitoring.component.ts#REQUEST_TIMEOUT_MS`), and an error says "The request to {namespace} timed out after 30 seconds.", the API's message, or that no answer came (`web-app/src/app/features/monitoring/monitoring.component.ts#failure`), with Retry; an error stays until a read succeeds. Counts are grouped by thousands, a subscription reads "topic / subscription", and dead-letter marks take the warning colours.

The Overview (2026-11-13, drawn from the `today` state of the monitoring artboard) holds four cards, Active and Dead-letter with their change since the last poll when it is not zero, Transfer and Monitored entities with the number of queues and subscriptions, the dead-letter card in the error container while any message is dead-lettered; the trend of the last polls as two sparklines, Active and Dead-letter, each an SVG coloured by the primary token with its first and last value and the time of the first and last poll (`web-app/src/app/features/monitoring/monitoring.component.ts#trend`), which replaced the ApexCharts chart and its literal colours; and the queues and the subscriptions as two `mat-table`s whose last column, Change, is the difference in active messages since the previous poll. Pinned by `web-app/src/app/features/monitoring/monitoring.component.spec.ts#the Overview says each total with its change since the last poll and draws the trend of active and dead-letter messages from the first poll to the last`.
Each poll of the snapshot, at the period chosen and never below 30 seconds, costs little: the table keeps a row element per entity (`trackBy` on the row key), `monitoring-counts` is `OnPush` and its state is all signals, and the All entities tab is created only when it is opened (`matTabContent`); the Overview deltas look the previous snapshot up in one map instead of a search per entity. Pinned by `web-app/src/app/features/monitoring/monitoring-counts.component.spec.ts` and `web-app/src/app/features/monitoring/monitoring.component.spec.ts`; the query values are encoded once by `apiPath` (`web-app/src/app/core/services/monitoring.service.spec.ts#names the queue, or the topic and the subscription, as query values encoded once`).

**Azure Monitor tab (2026-11-14).** On an Azure Service Bus connection a third tab, Azure Monitor, holds `app-monitoring-metrics` (`web-app/src/app/features/monitoring/monitoring-metrics.component.ts#MonitoringMetricsComponent`), created only when the tab is opened. It reads `GET metrics/connections/{id}` through `MetricsService.getNamespaceMetrics`, which passes errors on and has no fallback (`web-app/src/app/core/services/metrics.service.ts#getNamespaceMetrics`), for Last hour or Last day; a new range or leaving the tab cancels the read in flight, and Refresh reads again; there is no polling, each read is an Azure Monitor call. Six cards, Incoming, Outgoing, Active, Dead-lettered, Server errors and Throttled requests, each with its total (a count) or last value (a gauge) and an SVG sparkline in the primary token, broken where a grain is missing; a metric with no point says "No data". States, chosen from the API's `code` only, each with a fixed text: reading; "Metrics need a sign-in with Entra ID" for a connection string; "Metrics need the Azure resource ID of the namespace"; "Azure Monitor refused the read" naming the Monitoring Reader role, with Retry; "Could not read the metrics" with the sign-in or failed text and Retry. A failure draws no card. The chart is SVG, as the Overview's, not ApexCharts. Pinned by `web-app/src/app/features/monitoring/monitoring-metrics.component.spec.ts`. The connection form takes the optional "Azure resource ID" on every Azure connection (`web-app/src/app/features/connections/add-connection-dialog.component.ts#resourceIdError`).
