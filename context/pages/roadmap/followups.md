# Follow-ups

> One list, by risk. An entry is a pointer: the citation and the detail live under "Known gaps" on the service page named, so a line number is fixed in one place. A change that closes an entry removes it here and there in the same commit. Nothing on this list was fixed at the founding; the founding wrote it down.

Each entry carries its date. This page is a tracker: `version` changes only when its shape does.

## P1 - can lose a message or expose a secret

- **2026-11-12 - A RabbitMQ bulk operation addresses a message by its position (delete and move send first and remove after since 2026-11-16, resubmit since 2026-11-15).** A message removed by another client between the peek and the call shifts the ones behind it; a source with a consumer is refused, which narrows it. Closing it needs an identity checked under the hold, for instance the message id and the body hash the peek showed. The screen offers delete and move since 2026-11-16, with no Retry by position. [[pages/services/core/known-gaps-more]]
- **2026-11-12 - The consolidation migration still writes `workspace.json` directly**, not through the atomic save. [[pages/services/core]]
- **2026-11-13 - A legacy `connections.json` or `connection-groups.json` that cannot be parsed now stops the consolidation and is kept, but the app then starts with an empty workspace and tells the user nothing**; the first save creates `workspace.json` and the kept files are never read again. Nothing is lost on disk; the user has to know to recover them. [[pages/services/core]]
- **2026-11-12 - The single-message resubmit sends before it holds the original.** Since 2026-11-16 an original it could not remove is reported as a possible duplicate, no longer in silence; a message deep in the dead-letter queue is still sent and left there. Closing it means receiving the original first, as the batch does, which meets the scan limit of the entry below. [[pages/invariants/bulk-operations-are-at-least-once]]
- **2026-11-12 - Secrets are stored in plain text in `workspace.json`.** Not a breach of Rule G, which is about the boundary; an owner decision is needed on OS keychain or `safeStorage`. [[pages/services/core]]

- **2026-11-13 - The resubmit, delete and move scans reach only a few hundred messages past the head.** Measured on the emulator: a target about 300 deep in a dead-letter queue of 800 comes back "Not found within scan window" (pinned as a defect test), and consecutive calls can find their targets still locked by the previous call's prefetch. Delete and move share the same prefetch (`ScanPrefetchCount`), so the same exposure exists on `main`. Nothing is sent or removed when it happens, so no message is lost, but bulk work on a deep queue stops early. Owner decisions needed, after one measurement on a real namespace the owner names: hold the non-target locks until a bounded scan ends; or, for an unfiltered resubmit, receive the next batch from the head with no search; and where a message that fails to send then goes (deferring it inside the dead-letter queue changes its state). [[pages/conventions/decisions-that-look-like-defects]].

## P2 - weakens the API boundary

- **2026-11-12 - The loopback binding in `Program.cs` never runs under Electron** (`ASPNETCORE_URLS` is always set), and host filtering has two sources with no test sending a foreign Host. [[pages/services/api]], [[pages/invariants/local-authenticated-api]]
- **2026-11-12 - A malformed JSON request body gets the framework's automatic 400**, whose text may carry the parser's message (unverified). [[pages/services/api]]
- **2026-11-12 - The packaged window has no CSP.** [[pages/services/electron-shell]]
- **2026-11-12 - No code signing on any OS.** [[pages/services/electron-shell]]
- **2026-11-12 - If the API secret cannot be read, requests go out without the header** and fail as 401 with no message to the user. [[pages/services/web-app]]
- **2026-11-20 - A CORS preflight to `/mcp` is answered 204 before the MCP gate, even while the server is off.** It carries no MCP answer and allows only the front end's origins. [[pages/services/api/mcp-server]]

## P2 - correctness and lifecycle

- **2026-11-14 - The single-message actions fail on a session-enabled entity.** The dead-letter, defer and delete of one message scan with a non-session receiver, so on an entity that requires sessions the call fails; the actions are not hidden there. [[pages/services/core/azure-single-message-actions]]
- **2026-11-14 - A message whose body is an AMQP value or sequence cannot be peeked.** `ServiceBusReceivedMessage.Body` throws for it, and the read takes the body even for its size. [[pages/services/core/message-bodies]]
- **2026-11-12 - The delete-all decision compares the selection with the count the messages dialog received when it opened**, and an open messages dialog survives a change of connection from the Electron menu. [[pages/services/web-app]]
- **2026-11-12 - An entity named exactly `.` or `..` cannot be addressed**: the browser resolves it as a dot segment even when encoded, so deleting a subscription `..` under a topic would reach the topic's own route. Read from the URL standard and the route table, not run; RabbitMQ allows such names, Azure does not. [[pages/services/web-app]]
- **2026-11-12 - One static provider slot for the whole API process**, swapped and disposed while calls may be in flight; the monitoring service keeps a reference to a provider that may be disposed. [[pages/services/api]]
- **2026-11-12 - `import-full` is not atomic.** [[pages/services/api]]
- **2026-11-20 - An MCP tool call the SDK rejects before the tool runs is not recorded**, such as an argument of the wrong type, and the SDK logs it at Error. [[pages/services/api/mcp-server]]
- **2026-11-20 - An MCP client that names itself only in `initialize` is recorded as "Assistant"**: the stateless server reads the name from the request's `_meta`. [[pages/services/api/mcp-server]]
- **2026-11-20 - The toolbar reads the MCP state once at start**: if the API answers late or fails then, the MCP mark stays off until Settings is opened. [[pages/services/web-app/features-settings-mcp]]
- **2026-11-12 - Changing only the auth type, tenant, namespace or client secret skips the connection test on save.** [[pages/services/api]]
- **2026-11-12 - The SIGKILL fallback may not fire on a real quit** (Electron may exit before the timer; unverified), a tray click during the health wait opens the window early, and a crashed API is not restarted. The dialog wiring has no automated test. [[pages/services/electron-shell]]
- **2026-11-12 - After a cancelled bulk operation the list and counters are not reloaded; progress is one final update.** [[pages/services/web-app]]
- **2026-11-13 - Entity definitions leave out what the create options cannot carry and what was not verified**: the maximum message size of a Premium entity, a correlation rule property the app cannot write (type Other refuses the whole document), the size a partitioned Standard entity reports, user metadata against a broker (the emulator keeps none); the export reports no progress and the import creates one entity at a time. A namespace above 5000 queues, topics and subscriptions or 10000 rules is refused by the export (the bounds an import accepts); exporting it needs a chunked export into several files, not built. Deferred from item 4 of [[pages/roadmap/azure-service-bus-administration]]. [[pages/services/core]]
- **2026-11-12 - RabbitMQ members that throw or return empty behind the shared interface** (dead-lettering, search, sessions) and RabbitMQ logging through `Console.WriteLine`. [[pages/services/core]], [[pages/invariants/provider-boundaries]]

- **2026-11-13 - The end-to-end tests drive the renderer, not the desktop app.** They inject the two members of the preload contract into Chromium, so the API child process, the per-launch secret over IPC, the tray and the window frame are never exercised end to end. Next: one Playwright `_electron.launch` flow (add a RabbitMQ connection, connect, see the tree), and flows for resubmit, delete, purge, sessions, counts and definitions, which have none. [[pages/conventions/testing]].
- **2026-11-13 - Found by the end-to-end tests, not fixed:** the send dialog is cut off on its right edge at 1280 px wide; a RabbitMQ queue's panel shows Azure-only properties as 0 (delivery count, lock duration, size) instead of leaving them out. A RabbitMQ queue's dead-letter count, found here at 0, was fixed by the counts change. [[pages/conventions/testing]].

- **2026-11-14 - The single resubmit does not return the new message id it used.** The route answers `{ success: true }` only, so a copy sent under a new id cannot be traced from the app. [[pages/services/core/azure-bulk-safety-checks]]
- **2026-11-14 - The queue and topic lists do not carry `requiresDuplicateDetection`.** The Azure lists read runtime properties only, so a dialog opened from a list, or from a subscription, often offers "Send with a new message ID" only after a duplicate refusal. [[pages/services/web-app/bulk-new-message-id]]
- **2026-11-14** The Queues and Topics screens have no link in the desktop app, as the artboards draw three nav links; decide whether to remove those screens or draw a way to them. [[pages/services/web-app/known-gaps]]

- **2026-11-14 - A topic's scheduled messages are not listed.** On the emulator a peek on the topic path returns them (`src/ServiceBusExplorer.IntegrationTests/AzureServiceBusProviderTests.cs#On_the_emulator_a_peek_on_the_topic_path_returns_its_scheduled_messages`); the app asks for sequence numbers instead. Proposed: a read-only peek route on the topic, behind the key, over `PeekMessagesAsync` with no subscription, once real Azure behaviour is checked on a namespace the owner names. [[pages/services/core/azure-sub-queues]].

## P2 - performance

- **2026-11-13 - The RabbitMQ monitoring poll costs one management request per queue twice over.** A poll lists queues and exchanges (the topic list itself reads the queues and the bindings of each exchange), then per exchange its bindings, then for each queue binding the queue and its `.dlq` queue: about 3 + 2E + 2B requests for E exchanges and B queue bindings, every period. Since 2026-11-13 a binding to an exchange is no longer read as a queue. Left: one bindings lookup per topic where one `GET /api/bindings/{vhost}` would do, a topic read that needs only names, and the two queue reads per binding, which the queue list of the same poll already holds. [[pages/services/api]], [[pages/services/core]]
- **2026-11-13 - The monitoring store keeps 120 snapshots while the app reads 20.** The history route is asked for 20 (`count=20` in the web app), the store keeps 120 whole snapshots, one record per queue and subscription each. Estimate of the performance review, reasoned, not measured: about 200 bytes per entity per snapshot, so about 0.7 MB per snapshot and 80 MB held for 120 snapshots on a namespace of 3,500 entities, of the API's memory held for nothing the app reads. Either keep 20, or keep only the totals for the older ones. [[pages/services/api]]
- **2026-11-14 - The message list of the messages dialog is not virtualised.** Phase 4 of the Material migration asks for it; a peek of 1000 messages renders every row. [[pages/roadmap/ui-material-migration]]

- **2026-11-14 - A peek of an auto-forwarding queue fails with no explanation.** The broker refuses a browser on an entity with `ForwardTo`; the messages dialog should say so instead of a generic failure. Not done in the tree-marker change because another lane owned the dialog. [[pages/services/web-app/features-entities-main]]
- **2026-11-16 - The transfer dead-letter tab of a subscription fails to load.** On the emulator the broker refuses the peek of a subscription's transfer dead-letter queue with a general error, with and without a forward target, while a queue's answers empty. Since 2026-11-16 the peek answers 502 and the dialog says the broker did not return the messages, with the cause by name. Since later on 2026-11-16 the emulator declares no transfer dead-letter queue, so the tab is not offered on it. Left: real Azure was not verified, and Monitoring, the Queues and Topics pages and the dead-letter bell still show the emulator's zero counts. Phase 1 of [[pages/roadmap/rabbitmq-and-service-bus-completion]]. [[pages/services/core/azure-sub-queues]]
- **2026-11-16 - After a cancelled RabbitMQ resubmit the list may be read while the server still holds the messages**, for up to the confirm timeout, so the reload can show fewer rows than the queue has. Nothing is sent or lost. The fix is on the server: answer the cancel after the channel is closed. Phase 3 of [[pages/roadmap/rabbitmq-and-service-bus-completion]]. [[pages/services/core/rabbitmq-and-legacy]]
- **2026-11-16 - The dead-letter bell, the Queues and Topics pages and Monitoring keep their own copy of the counts**, each refreshed on its own trigger, so they can disagree with the tree, the panel and the messages dialog, which read one signal since 2026-11-16. The scheduled, transfer and transfer dead-letter counts are not in that signal either. [[pages/services/web-app/features-entities-panel-and-definitions]]
- **2026-11-14 - Subscriptions carry no status or forward target in the tree.** `GetSubscriptionsAsync` lists runtime properties only, so a disabled or forwarding subscription has no marker; the same configuration join as the queue list would cost one call per page. [[pages/services/core/azure-provider]]
- **2026-11-14 - `MetricsService` per-entity reads still fall back to random data on an error.** `getQueueMetrics`, `getTopicMetrics` and `getSubscriptionMetrics` return generated series on any failure but 503; no screen calls them. Remove the fallback, or the three methods, before any screen does. The namespace read has no fallback.
