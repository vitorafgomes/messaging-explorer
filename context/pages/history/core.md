# Core history

What changed when in the project [[pages/services/core|Core]] describes, newest first.

## 2026-11-16

- The RabbitMQ provider writes to the application's logger, no longer to the console (`src/ServiceBusExplorer.Core.Tests/Providers/RabbitMQLoggingAndDatesTests.cs#A_connection_test_the_broker_does_not_answer_is_a_warning_in_the_application_log_with_no_password_and_nothing_on_the_console`), and a queue or an exchange carries no date, because the broker reports none. The gap "RabbitMQ logs to the console" is closed.

- The Azure capabilities follow the connection: the development emulator declares no message counts and no transfer dead-letter queue. [[pages/services/core/azure-sub-queues]]

- RabbitMQ receive and purge on a stream are refused before the broker is asked; either one closed the whole connection. RabbitMQ search throws and `SupportsMessageSearch` is declared; it answered an empty result ([[pages/services/core/rabbitmq-and-legacy]]).

- A batch failure carries `PossibleDuplicate`, set by both providers where a message was sent, or may have been, and was not removed; the web app read it from the words of the text.
- Azure single resubmit. Was: when the original could not be removed after the copy was sent, the call returned as if all was done. Is: it throws `InvalidEntityConfigurationException` with the possible-duplicate sentence, which the route answers as a 400 ([[pages/invariants/bulk-operations-are-at-least-once]]). `Defect_single_resubmit_of_a_message_deep_in_the_dead_letter_queue_sends_it_and_leaves_it_there` changed on purpose: it now expects that sentence.
- Closed without a change, on reading the code and its tests: a send that fails partway through a resubmit or move cycle has reported its messages as possible duplicates since 2026-11-13 (`src/ServiceBusExplorer.Core.Tests/Providers/Azure/AzureServiceBusProviderSubQueueTests.cs#A_resubmit_or_move_whose_second_send_times_out_reports_both_sends_as_possible_duplicates_and_nothing_as_not_found`); the follow-up that said otherwise was stale.

- RabbitMQ send. Was: published on the shared channel with no `mandatory` and no confirm, to an exchange when the message had a subject and to the default exchange otherwise. Is: confirmed, on a channel of its own, to the queue of that name or else the exchange ([[pages/services/core/rabbitmq-and-legacy]]). `Defect_send_to_a_fanout_exchange_without_subject_is_dropped_and_reports_success` changed on purpose; the setup of `RabbitMQSendBatchTests` gained a confirm and the send's own channel, its assertions are the same.
- RabbitMQ peek. Was: a refusal left the provider as an exception of the RabbitMQ client, and a peek of a stream closed the connection. Is: `MessageReadFailedException`, and a stream is refused before the broker is asked.

- `SupportsBulkMessageOperations` is true for RabbitMQ; it was false since 2026-11-15. `RabbitMQ_declares_no_bulk_message_operations_and_Azure_Service_Bus_does` changed on purpose into `RabbitMQ_and_Azure_Service_Bus_both_declare_bulk_message_operations_and_only_RabbitMQ_names_a_message_by_position`.

- RabbitMQ bulk delete and move. Was: both consumed up to the highest position through the management API and republished, so a failed or unrouted republish lost the message, the token was never read and move ignored the subscription. Is: both run on the resubmit's send-first path ([[pages/services/core/rabbitmq-and-legacy]]). `Defect_move_to_a_missing_queue_reports_success_and_the_message_is_gone` changed on purpose into `A_move_to_a_missing_queue_reports_the_failure_and_the_message_stays_in_the_source`.

- Azure peek, the broker not answering. Was: any broker failure of a peek but a disabled entity left the provider as the SDK's `ServiceBusException`. Is: it leaves as `MessageReadFailedException` with a fixed sentence and the failure reason by name ([[pages/services/core/azure-sub-queues]]). Three tests of `AzureServiceBusProviderSubQueueTests.cs` changed on purpose: they asserted the SDK type and now assert the neutral one with the SDK error as its inner exception.

- RabbitMQ resubmit, the close that proves the removals. Was: only a closed channel, an interrupted operation or an I/O error from the close counted as an unproven removal; any other exception, a timeout among them, left the call with no result, so the messages already sent were not reported. Is: any exception from the close reports each sent message as a possible duplicate (`src/ServiceBusExplorer.Core/Providers/RabbitMQ/RabbitMQProvider.cs#RemovalsSettled`). New test: `src/ServiceBusExplorer.Core.Tests/Providers/RabbitMQResubmitFailureTests.cs#A_close_that_times_out_leaves_the_removal_unproven_and_reports_the_sent_message_as_a_possible_duplicate` ([[pages/services/core/rabbitmq-and-legacy]]).

## 2026-11-15

- RabbitMQ: a message published with no property, which the management API writes as `"properties": []`, no longer breaks the bulk reads (a delete consumed the messages and then threw); a peek of the dead-letter side of a queue with no `<queue>.dlq` answers empty; and a channel the broker closed is opened again, so one missing queue no longer breaks every later call ([[pages/services/core/rabbitmq-and-legacy]]). Found in the owner's hand test.
- RabbitMQ peek returns each message once, in queue order: it holds what it read and requeues it all at the end, also on an error or a cancel; before, it returned the head message N times.
- RabbitMQ peek numbers each message with its position, the key of the bulk delete, move and resubmit: one click no longer ticks every row, and with one row loaded a delete no longer becomes a purge. Found in the owner's hand test.
- RabbitMQ resubmit rebuilt over AMQP: publish with a confirm, then acknowledge; the chosen position is the one sent; a consumer on the dead-letter queue refuses it (owner asked for Resubmit beside Auto resubmit, 2026-11-15).
- `SupportsBulkMessageOperations`: true for Azure Service Bus, false for RabbitMQ, whose bulk calls consume before they republish; the screen hides them there (owner's decision, 2026-11-15).
- The masked list and get name an Azure connection's endpoint host as its namespace, read by `AzureConnectionConfig.EndpointHost`, which keeps neither the key nor user info ([[pages/services/core/workspace-and-metrics]]).

## 2026-11-14

- Message bodies that are not valid UTF-8 are read as the base64 of their exact bytes with `BodyEncoding`, never with replaced bytes, and a base64 body is sent byte for byte ([[pages/services/core/message-bodies]]); one active message is dead-lettered or deferred by a bounded scan ([[pages/services/core/azure-single-message-actions]]). The topic listing's failing call and the metrics credential after a secret rotation are pinned by tests.
- **Namespace metrics and list status.** `AzureNamespaceMetricsReader` reads six Azure Monitor metrics of a connection's `AzureResourceId` with its Entra ID credential, refusing a connection string and a missing resource ID before any call (`src/ServiceBusExplorer.Core/Providers/Azure/AzureNamespaceMetricsReader.cs#ReadAsync`); the queue and topic lists join the configuration listing for status and forward target (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#ListQueuesCoreAsync`).
- **Scheduled messages of a topic can be cancelled, and a scheduled send returns its sequence number.** `CancelScheduledMessagesAsync` takes a queue or a topic; `SendMessageAsync` returns `long?` through `ScheduleMessageAsync` when a time is set. [[pages/services/core/azure-sub-queues]].
- **One proxy rule for every write of a connection.** `src/ServiceBusExplorer.Core/Models/ServiceBusConnection.cs#HasAllowedProxy` allows on Azure Service Bus what `AzureConnectionConfig.IsProxyAllowed` allows and no proxy on RabbitMQ; `src/ServiceBusExplorer.Core/Services/FileWorkspaceManager.cs#SaveConnectionAsync` and `#ImportConfigurationAsync` throw `ArgumentException` with the fixed `ProxyRefusal` and store nothing. A RabbitMQ save used to store a proxy with a password.
- **The namespace properties are read.** `IMessagingProvider.GetNamespacePropertiesAsync` (`src/ServiceBusExplorer.Core/Abstractions/IMessagingProvider.cs#GetNamespacePropertiesAsync`) and the capability `SupportsNamespaceProperties`: Azure reads name, tier, messaging units, geo-DR alias and times in one administration call (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#GetNamespacePropertiesCoreAsync`) and gives the tier's largest message, 256 KB on Basic and Standard, 100 MB on Premium (`src/ServiceBusExplorer.Core/Models/NamespaceInfo.cs#MaxMessageSizeInBytes`); RabbitMQ declares none and refuses the read. `AzureProviderCapabilities.MaxMessageSizeInBytes` stays 256 KB, now named the default used while the tier is not known.
- **An Azure connection chooses its transport and an optional proxy.** `ServiceBusConnection` and `AzureConnectionConfig` carry `UseWebSockets` and `ProxyAddress`; the messaging client is built with AMQP over WebSockets on 443 when asked, and both clients go through the proxy with the default credentials of this computer (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#BuildClientOptions`, `src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#BuildAdministrationClientOptions`). A proxy with a user name or password, or without WebSockets, is refused by `src/ServiceBusExplorer.Core/Providers/Azure/AzureConnectionConfig.cs#IsProxyAllowed`, used by `IsValid` and by the import; no proxy credential is stored. The mask and the merge carry both fields ([[pages/services/core/azure-provider]]).
- The deferred resubmit's possible-duplicate text is fixed, with no broker text (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#DeferredDuplicateError`); a failing send, a second batch that fails and an unreadable target are pinned by tests.
- **Deferred messages can be deleted, resubmitted and dead-lettered by sequence number.** Three members of `IMessagingProvider` (`src/ServiceBusExplorer.Core/Abstractions/IMessagingProvider.cs#DeleteDeferredMessagesAsync`, `src/ServiceBusExplorer.Core/Abstractions/IMessagingProvider.cs#ResubmitDeferredMessagesAsync`, `src/ServiceBusExplorer.Core/Abstractions/IMessagingProvider.cs#DeadLetterDeferredMessagesAsync`), 1 to 1000 numbers in batches of 100, send before complete, a number that is not deferred reported "Not found as a deferred message." (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#SettleDeferredCoreAsync`). `SupportsDeferral` is true again for Azure, reversing the 2026-11-12 decision that declared it false because nothing deferred; RabbitMQ refuses with a fixed text. `CheckBeforeScanAsync` takes a null sub-queue for a call that reads no source setting, and `ValidateScheduledSequenceNumbers` takes its bound. [[pages/services/core/azure-deferred]].

- A batch the broker refuses midway as disabled is never listed with a new message id: it sent nothing (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#SendResubmitBatchAsync`), pinned by `src/ServiceBusExplorer.Core.Tests/Providers/Azure/AzureServiceBusProviderSubQueueTests.cs#A_batch_the_broker_refuses_midway_as_disabled_is_never_listed_with_a_new_message_id`.
- **The single resubmit no longer loses a message into a target with duplicate detection.** `ResubmitDeadLetterMessageAsync` runs `CheckBeforeScanAsync` on its target before it peeks or sends and throws `InvalidEntityConfigurationException` with the fixed text on a refusal; it takes `newMessageIdOnDuplicateDetection` and sends the copy with a new id and `x-original-message-id` (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#ResubmitDeadLetterMessageAsync`, `src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#GiveNewMessageId`). The unreadable-settings text now names the Manage right, and a dead-letter delete reads no settings at all (owner decision). `UnselectedDeadLettered` is documented as a lower bound, like `UnselectedDeliveryCountRaised`. [[pages/services/core/azure-bulk-safety-checks]].
- **A resubmit or move into a target with duplicate detection no longer loses the message, and a selective delete or move on an active entity no longer dead-letters unselected messages silently.** `CheckBeforeScanAsync` reads the target's duplicate detection and the source's max delivery count before any receive and refuses every message per sequence number when the copy would be dropped, when one receive would dead-letter, or when the read fails; `newMessageIdOnDuplicateDetection` sends each copy under a new id with `x-original-message-id`; `RecordReleases` stops the scan before an unselected message reaches its limit. `BatchOperationResult` gains `NewMessageIds`, `UnselectedDeliveryCountRaised` and `UnselectedDeadLettered` (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#CheckBeforeScanAsync`, `src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#RecordReleases`). The integration fixture's messaging provider now carries the HTTP administration client (`src/ServiceBusExplorer.IntegrationTests/AzureServiceBusFixture.cs#ConnectMessagingAsync`).
- `IMessagingProvider.SendMessagesAsync` returns `SendMessagesResult` and takes a token. Azure splits by size (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs#SendInBatchesAsync`), refuses a single message too large for a batch, and returns a partial result after the first accepted batch; RabbitMQ awaits each publish. `SupportsTransactions` is false in `src/ServiceBusExplorer.Core/Providers/Azure/AzureProviderCapabilities.cs#SupportsTransactions` and `src/ServiceBusExplorer.Core/Providers/RabbitMQ/RabbitMQProviderCapabilities.cs#SupportsTransactions`: no code runs a transaction.
- **The display target of a connection string never reaches its key.** `AzureConnectionConfig` cut the host at the first `.` after `Endpoint=sb://`, so a host without a dot (`localhost`, an emulator) followed by any later dot gave a target that carried `SharedAccessKeyName` and the key; that target is answered by connect, written to the connect log line and, since 2026-11-14, to an exported definitions file as `source`. The host now ends at the first `.`, `:`, `/` or `;` (`src/ServiceBusExplorer.Core/Providers/Azure/AzureConnectionConfig.cs#HostEnd`), pinned with a sentinel key by `src/ServiceBusExplorer.Core.Tests/Providers/Azure/AzureConnectionConfigTests.cs#The_display_target_of_a_connection_string_is_its_host_alone_and_never_reaches_the_key`, which failed before the change with the target "localhost;SharedAccessKeyName=K;SharedAcc...".
- **2026-11-14** `EntityDefinitionsDocument.Source` and `DefinitionImportItem.Differences` (`DefinitionFieldDifference`): the Azure dry run gives each differing setting its value on the broker and in the document; `DifferingFields` derives from the same list.
- **2026-11-14** The topic read carries each subscription's status and rule count (Azure, bounded and cancellable) and the bound queues' real state and counts (RabbitMQ); `GetTopicAsync` takes a token.
- **2026-11-14** `ConnectionGroup.IsProduction`, the TLS flags `UseSsl` and `UseManagementSsl`, and `MarkUsedAsync`, so the last use survives an edit save.
