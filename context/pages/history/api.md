# Api history

What changed when in the project [[pages/services/api|Api]] describes, newest first.

## 2026-11-20

- From an outside review of the MCP server: turning it off or creating a token ends every request waiting for the user or the app at once, and withdrawing the choice of the settings of the app ends those for the app; the tool is refused with "The MCP server was turned off.", "The MCP token was replaced." or the not-allowed sentence and does nothing, and the app's answer while the choice is off is 404 ([[pages/services/api/mcp-app-settings]]).

- From the same review: a failed removal in a delete, resubmit or move reaches a route and an MCP answer as a fixed sentence for its kind of failure, never the broker's text ([[pages/services/core/azure-bulk-operations]]).

- From the review of the app settings tools: the test that no record line or request holds the token or the key now reads the request while it waits and checks both secrets, and it and the reason test were each shown red by a mutation (`src/ServiceBusExplorer.Api.Tests/McpAppSettingsTests.cs#No_record_line_holds_the_token_or_the_key_whatever_an_assistant_passes`).

- An assistant reads and changes the theme, Developer mode and the update channel of the app, when the user allowed it in Settings (ADR 0008, the settings of the app): `read_app_settings` and `change_app_setting`, refused while `appSettingsAllowed` is false, off by default; only those three settings and their fixed values are handed to the app, through `GET api/mcp/app-requests` and `POST api/mcp/app-requests/{id}/answer`, at most 20 waiting for at most ten seconds; `PUT api/mcp/app-settings` turns the choice on and off. `supports.appSettings` is true. [[pages/services/api/mcp-app-settings]]

- From the review of the tools that administer entities: a name with a space at an edge, a control character or more than 260 characters is refused before anybody is asked, in those tools and in the ones that move and remove, because the request showed and asked the user to type the cleaned name while the broker was given the raw one (`src/ServiceBusExplorer.Api/Mcp/McpToolCalls.cs#RequireExactNames`).

- The MCP server creates, changes and deletes entities, asking the user first (ADR 0008, fourth phase): twelve tools, `create_`, `update_` and `delete_` of queues, topics, subscriptions and rules, on a connection offered at `all`, each always asked, a delete with the name typed; capabilities, a blank or renamed name and the lookups the request needs refuse before anybody is asked. After the allow each runs its route's body, now one internal method per route in `QueuesController` and `TopicsController`, with unchanged answers; a create or delete whose route has no body answers `{ success: true }`. `supports.entities` is true. [[pages/services/api/mcp-administering-entities]]

- From the review of the tools that move and remove: each tool whose lookup of its queue, subscription or topic fails answers the fixed sentence, asks nobody and does nothing (`src/ServiceBusExplorer.Api.Tests/McpRemoveToolTests.cs#A_tool_whose_lookup_of_its_entity_fails_answers_the_fixed_sentence_asks_nobody_and_does_nothing`); a level that does not exist covers nothing (`src/ServiceBusExplorer.Api/Mcp/McpSettingsStore.cs#Covers`).

- Five defects of the MCP server found by calling the running app against local test brokers: `move_messages` looks its target up before anybody is asked and refuses one that does not exist with "The target was not found."; a send to a queue that requires sessions with a message without a `sessionId` is refused with a fixed sentence before anybody is asked, instead of failing in the broker SDK; `reason` is optional in the schema of the send tools, connect_to and the six tools that move and remove, and a call without one, or with a blank one, is refused by the tool and recorded instead of rejected by the SDK with an Error line; tool answers carry enums by name (`filterType`, a correlation property's `type`); the three lists leave `status` out when the provider gives none. [[pages/services/api/mcp-server]], [[pages/services/api/mcp-asking-and-sending]], [[pages/services/api/mcp-moving-and-removing]]

- The MCP server moves and removes messages, asking the user first (ADR 0008, third phase): a third level, `all`, which covers the two before it; `dead_letter_messages`, `resubmit_messages`, `move_messages`, `delete_messages`, `purge_messages` and `cancel_scheduled_messages` on a connection offered at it, each always asked, never-asked mark or not, refused by capability and, for the five that take sequence numbers, on a provider that names a message by its position, before anybody is asked. A request carries `danger` and `typed`; an allow of a delete or a purge needs the name typed exactly, else 400 and the request keeps waiting. After the allow each runs its route's body, now one internal method per operation in `QueuesController` that the queue and the subscription routes call too, with unchanged answers. [[pages/services/api/mcp-moving-and-removing]]

- From the review of `connect_to`: a stored connection removed under its offer while the user was being asked is refused after the allow and nothing connects (`src/ServiceBusExplorer.Api.Tests/McpConnectToolTests.cs#A_connect_allowed_after_the_stored_connection_was_removed_under_its_offer_is_refused_and_connects_nothing`).

- The MCP server switches the active connection, asking the user first: `connect_to(connection, reason)` takes an offered connection by id or exact name, answers at once for the one already active, otherwise always asks (kind `connect`, never-asked or not), checks the offer again after the allow and connects through `src/ServiceBusExplorer.Api/Controllers/ConnectionsController.cs#ConnectStoredAsync`, now the one body of `POST api/connections/{id}/connect` too, whose answers are unchanged. A failed connect answers the route's fixed sentence and leaves the active connection as it was (`src/ServiceBusExplorer.Api.Tests/McpConnectToolTests.cs#A_connect_that_fails_answers_the_fixed_sentence_of_the_route_and_leaves_the_active_connection_as_it_was`). [[pages/services/api/mcp-asking-and-sending]]

- From the review of the sending phase of the MCP server: a send whose lookup of the entity fails answers the fixed sentence, asks nobody and sends nothing (`src/ServiceBusExplorer.Api.Tests/McpSendToolTests.cs#A_send_whose_lookup_of_the_entity_fails_answers_the_fixed_sentence_asks_nobody_and_sends_nothing`); a lookup of a topic that fails is covered too; the per-message report of `send_messages`, its bound of 100 (the call of 101 no longer waits for a user in the test), the fixed sentence of a failed send and that a failed send is not sent again were each proven by a mutation; the note of a send to a topic says the subscriptions the messages match, which is true on RabbitMQ too.

- The MCP server sends, asking the user first (ADR 0008, second phase): `send_message` and `send_messages` on a connection offered at `readAndSend`; each send, and each read of a production connection, waits up to two minutes for the user's answer in the app through `GET api/mcp/requests` and `POST api/mcp/requests/{id}/answer`, behind the key; denied, unanswered or cancelled sends nothing; at most 20 wait. A production connection can be offered, and a local test broker marked as never asked. [[pages/services/api/mcp-asking-and-sending]]

- The MCP server after its review: a refusal is answered as an error result, no longer logged at Error by the SDK, and a broker failure keeps only its own Warning line; `list_queues` and `list_subscriptions` answer `countsAvailable` and leave counts out where the broker gives none; `peek_messages` answers `{ messages }`, says what a peek costs on RabbitMQ in its description and in a `note`, and is no longer marked read-only nor declared non-destructive; the entity named by an assistant is recorded cut at 100 characters; every capability guard and the unknown level of `read_logs` are fired by a test (`src/ServiceBusExplorer.Api/Mcp/McpReadTools.cs#Call`, `src/ServiceBusExplorer.Api/Mcp/McpReadTools.cs#RabbitMQPeekNote`, [[pages/services/api/mcp-server]]).

- An operation the broker refuses as not authorised answers 502 with a fixed sentence saying what it needs, on every route, where it was the constant 500; the owner's log lines showed the refusal on reads and it can happen on any operation (`src/ServiceBusExplorer.Api/Controllers/EntityAdministrationResults.cs#Unhandled`, `src/ServiceBusExplorer.Api.Tests/MessageRouteTests.cs#An_operation_the_broker_refuses_as_not_authorised_answers_502_saying_what_it_needs_and_nothing_of_the_broker`).

- The Logs route and the in-memory store of the last 2000 lines, without the text of any exception. [[pages/services/api/controllers]]

- The connect route answers `credentials-refused` with a fixed sentence when the broker refused the user name or the password.

- `api/azure-directory`: sign in, the subscriptions, the namespaces of one, sign out; the token reaches no response and no log. [[pages/services/api/controllers]]
