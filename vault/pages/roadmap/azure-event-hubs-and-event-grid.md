# Azure Event Hubs and Azure Event Grid: the Microsoft Azure family

> The next version adds two Microsoft products that are not queues: Event Hubs is a partitioned log that is read from a position and never emptied, and Event Grid is a router whose push side can only be published to and whose pull side behaves like a small queue. This page says how they appear beside Service Bus, how they fit a code base shaped for queues, and what to build per layer.

## Where this comes from

On 2026-11-12 the owner decided that the next version adds Azure Event Hubs and Azure Event Grid, with the Microsoft products presented together (Service Bus, Event Hubs, Event Grid as one "Microsoft Azure" family), and asked for "the full survey for it". The reference tool, Paolo Salvatori's Service Bus Explorer, was read from its README, `EventGridExplorer_README.md`, `NEWFEATURES.md`, `docs/documentation.md` and the controls under `src/ServiceBusExplorer/Controls/` and `src/EventGridExplorerLibrary/` (https://github.com/paolosalvatori/ServiceBusExplorer); its `CHANGELOG.md` says nothing on either product. It supplies ideas only: its Event Hubs screens run on `WindowsAzure.ServiceBus` 7.0.1 and its Event Grid library on beta packages. The entry of [[pages/roadmap/product-backlog]] points here; the Service Bus work is on [[pages/roadmap/azure-service-bus-administration]], whose shape this page follows.

Three rules the owner set:

- **Current SDKs only.** `Azure.Messaging.EventHubs` 5.12.2, `Azure.Messaging.EventGrid` 5.0.0, `Azure.Messaging.EventGrid.Namespaces` 1.1.0, `Azure.ResourceManager` 1.14.0 with `.EventHubs` 1.3.0, `.EventGrid` 1.1.0, `.ServiceBus` 1.2.0 and `.ResourceGraph` 1.1.1, and the `Azure.Identity` 1.21.0 already referenced (`src/ServiceBusExplorer.Core/ServiceBusExplorer.Core.csproj:14`). Versions are the latest stable on NuGet on 2026-11-12 (https://api.nuget.org/v3-flatcontainer/azure.messaging.eventhubs/index.json and the same path per package id). Never `Microsoft.Azure.EventHubs` (deprecated on NuGet, obsolete since 2025-12-31, https://www.nuget.org/packages/Microsoft.Azure.EventHubs), `WindowsAzure.ServiceBus` or `Microsoft.Azure.EventGrid` (deprecated, obsolete since 2023-03-31, https://www.nuget.org/packages/Microsoft.Azure.EventGrid). **One conflict with the rule as stated:** `Azure.Monitor.Query`, which the rule names and the code references at 1.7.1 (`src/ServiceBusExplorer.Core/ServiceBusExplorer.Core.csproj:16`), is itself deprecated on NuGet since 2025-10-16 (https://www.nuget.org/packages/Azure.Monitor.Query); its metrics client moved to `Azure.Monitor.Query.Metrics` (https://github.com/Azure/azure-sdk-for-net/blob/main/sdk/monitor/MigrationGuide_Query.md). See item M and the open questions.
- **Performance is part of the design.** Each item states its round trips, its paging and its bounds.
- **Security is part of the design.** Each item names the rules of the root `CLAUDE.md` it touches (A, F, G, H) and the confirmation a state-changing action needs under [[pages/conventions/ui]] rule 6.

**Out, and why.** Azure Relay and Notification Hubs: different products, and the reference tool reaches them only through the legacy library. The Kafka endpoint of Event Hubs (https://learn.microsoft.com/en-us/azure/event-hubs/azure-event-hubs-apache-kafka-overview): a second protocol and client for the same data the AMQP client reads. The MQTT broker of Event Grid namespaces (https://learn.microsoft.com/en-us/azure/event-grid/mqtt-overview): a device protocol with its own client model, not a messaging entity to browse. Capture (https://learn.microsoft.com/en-us/azure/event-hubs/event-hubs-capture-overview): its output is files in a storage account; the setting is shown read-only at most. Schema Registry editing (https://learn.microsoft.com/en-us/azure/event-hubs/schema-registry-overview, `Azure.Data.SchemaRegistry`): mentioned only; decoding a body through a schema is a later idea. Geo-replication settings: read-only flag at most.

## What the two products are, in the terms of this code base

- **Event Hubs is a log, not a queue.** A hub has a fixed set of partitions; a reader chooses a consumer group, a partition and a starting position, and reading removes nothing: events "are available to all consumers and are not removed from the partition when read" (https://github.com/Azure/azure-sdk-for-net/blob/main/sdk/eventhub/Azure.Messaging.EventHubs/samples/Sample05_ReadingEvents.md). Events leave only by retention (1 day on Basic, 7 on Standard, 90 on Premium and Dedicated, EH-QUOTA). There is no delete, no dead-letter queue, no lock, no delivery count.
- **Event Grid is two worlds.** (a) Custom topics, system topics, domains and partner topics deliver by push to a destination; the data plane can only publish (`EventGridPublisherClient` is the whole client surface, EG-API) and everything a user would browse (topics, event subscriptions, filters, destinations) is the management plane. (b) Event Grid namespaces hold namespace topics with pull delivery, where the data plane can publish, receive, acknowledge, release, reject and renew locks (NS-API): close to a queue, with lock tokens in place of sequence numbers and no peek.
- **The data plane of neither product can list anything.** An Event Hubs client is bound to one hub and exposes only that hub's properties and partitions (EH-API, by absence of any list member); both Event Grid namespace clients take the topic name in the constructor (NS-API). Listing hubs, consumer groups, topics and event subscriptions is `Azure.ResourceManager.*`, which needs an Entra identity, a subscription and a control-plane role. This one fact drives the connection model below.

## How the family appears to the user

**What exists.** A connection is one saved endpoint with a provider type (`src/ServiceBusExplorer.Core/Models/ServiceBusConnection.cs:26`); the dialog offers two providers (`web-app/src/app/features/connections/add-connection-dialog.component.ts:461`) and four of the five Azure credential types (`web-app/src/app/features/connections/add-connection-dialog.component.ts:482`); an identity connection still asks the user to type the namespace (`src/ServiceBusExplorer.Core/Models/ServiceBusConnection.cs:117`). Resource discovery, the half of [[pages/decisions/0003-azure-authentication-strategy]] that delivers its stated requirement, was never built.

**What a connection string can and cannot identify.**

- An Event Hubs connection string has the same shape as a Service Bus one, `Endpoint=sb://<ns>.servicebus.windows.net/;SharedAccessKeyName=..;SharedAccessKey=..`, with an optional `;EntityPath=<hub>` (https://learn.microsoft.com/en-us/azure/event-hubs/event-hubs-get-connection-string). The string does not say which product the namespace is: the user must, and today's validity check accepts both (`src/ServiceBusExplorer.Core/Providers/Azure/AzureConnectionConfig.cs:87`).
- It identifies a namespace and at most one hub. It carries no subscription id and no resource group, so it cannot reach the management plane: with a connection string the app cannot list hubs or consumer groups, and cannot read metrics. The user types the hub name unless `EntityPath` supplies it (`EventHubsConnectionStringProperties.Parse`, member `EventHubName`, EH-API), and types a consumer group other than `$Default`.
- A namespace REST listing exists (`GET https://{ns}.servicebus.windows.net/$Resources/Eventhubs`, https://learn.microsoft.com/en-us/rest/api/eventhub/list-event-hubs) under a section titled "classic" with a retirement banner whose scope is ambiguous; no current SDK library wraps it. Under rule 1 it is not used. Whether it is still supported: not verified.
- Event Grid has no connection string. A topic is an endpoint URL plus an access key, a SAS or an Entra token (EG-API constructors); a namespace topic is the namespace endpoint, a topic name and, to receive, a subscription name (NS-API).

**Recommendation: one Microsoft Azure sign-in that discovers, and one connection per resource.**

1. A new first step in the add-connection flow, "Microsoft Azure", with two paths: **Sign in and browse** (interactive browser, Azure CLI, service principal or default chain, the credentials ADR 0003 already allows) and **Enter manually** (connection string or endpoint and key, per product).
2. After sign-in the app lists, in one tree, what the identity can see: subscription, then product (Service Bus namespaces, Event Hubs namespaces, Event Grid namespaces, topics, domains and system topics), then the resource. The user picks one or several; each becomes a saved connection of its product that stores the credential type, the fully qualified namespace or endpoint and the ARM resource id, and no secret. This is ADR 0003 point 2, built for three products at once.
3. In the connections list the three products sit under one "Microsoft Azure" heading with a product icon each; RabbitMQ stays beside it. Client and environment groups work as today.
4. Once connected, the tree is the product's own shape: Service Bus as today; Event Hubs as hub, then Partitions and Consumer groups; an Event Grid namespace as topic, then event subscriptions; an Event Grid topic, domain or system topic as its event subscriptions.

A connection that carries an ARM resource id gets the management features (list hubs, consumer groups, event subscriptions, metrics); a manual one gets the data plane only, and the screen says why the rest is absent ([[pages/conventions/ui]] rule 9: an explained state, not an empty list).

**The alternative: one "Azure account" connection with every product under it.** The tree would be subscription, product, namespace, entity, all live at once. It reads best and it is what "together" suggests, but it needs several active providers in one API process, which the code cannot do today (next section), a different saved-connection shape, and an answer to what client, environment and the environment badge mean for a connection that spans production and test subscriptions. It is the right second step once the active provider leaves the static slot, the same precondition as "several namespaces at once" on [[pages/roadmap/product-backlog]]. The recommendation is built so that step does not undo it: discovery, credentials and the per-product panels are the same.

## How it fits the code, honestly

`IMessagingProvider` is shaped for queues, topics and subscriptions with destructive message operations (`src/ServiceBusExplorer.Core/Abstractions/IMessagingProvider.cs:11`). Member by member:

**What the interface lacks.** For Event Hubs: partitions and their properties, a starting position (earliest, latest, sequence number, offset, enqueued time), a consumer group on every read, read without remove as the only read, and an offset that is a string. For Event Grid namespaces: lock tokens, acknowledge, release with a delay, reject, renew, and a per-token result. For push topics: nothing on the data side beyond publish; the rest is a read-only view of management-plane objects (filters, destinations, retry policy) that has no counterpart in `IMessagingEntity` (`src/ServiceBusExplorer.Core/Abstractions/IMessagingEntity.cs:7`). `IMessage` assumes a delivery count, a dead-letter reason, a time to live and a numeric sequence number (`src/ServiceBusExplorer.Core/Abstractions/IMessage.cs:56`, `src/ServiceBusExplorer.Core/Abstractions/IMessage.cs:104`); an event has an offset, a partition and system properties instead.

**The options.**

1. **Stretch the interface with capabilities.** Two new `ProviderType` values implement all of `IMessagingProvider`; hubs pose as topics and consumer groups as subscriptions; about three quarters of its thirty eight members throw `NotSupportedException` behind new false flags; new members (partitions, positions, lock tokens) are added and the Service Bus and RabbitMQ providers must refuse each one ([[pages/invariants/provider-boundaries]], change protocol). Cost against Rule F: the letter is kept and the purpose is lost, since most of the contract becomes members that exist to be refused, the "RabbitMQ members that throw behind the shared interface" gap of [[pages/roadmap/followups]] multiplied by two products. The one shared panel (`web-app/src/app/features/entities/entities-container.component.ts:20`) would need a flag for nearly every control. Cheapest to start, most expensive to keep.
2. **A second abstraction for streams.** An `IEventStreamProvider` (hubs, partitions, consumer groups, read from a position, send) implemented by Event Hubs. Cost against Rule C: one implementer. The second would be Kafka, for which the repository holds an empty folder and a TODO (`web-app/src/app/providers/kafka/index.ts:4`) and no decision; an interface drawn from one product gets the second one wrong. Event Grid fits it no better than it fits the queue interface, so a third abstraction would follow.
3. **One provider per product, sharing only what all four have.** Split `IMessagingProvider`: the connection members (`src/ServiceBusExplorer.Core/Abstractions/IMessagingProvider.cs:18` to `src/ServiceBusExplorer.Core/Abstractions/IMessagingProvider.cs:58`) become a small base contract that the four providers implement, which is an abstraction with four users; the queue, topic, subscription and message members stay on the existing interface, implemented by Service Bus and RabbitMQ only, unchanged. Event Hubs and Event Grid each get a provider class under their own folder (`Providers/AzureEventHubs/`, `Providers/AzureEventGrid/`) whose public surface uses neutral models only (hub, partition, event, event subscription, lock result), and each gets its own controllers. No stream interface, no Event Grid interface, until a second broker of the same shape exists. Cost against Rule F: its sentence "a broker is reached through `IMessagingProvider`" stops being true for two products and must be reworded to what it protects, that no `Azure.*` type leaves a provider folder and that what a provider cannot do is declared, never a silent no-op. Cost against Rule C: none.

**Recommendation: option 3.** It adds no member that exists to be refused, it leaves the two working providers and their tests untouched, and it draws no abstraction from a single example. `IProviderCapabilities` (`src/ServiceBusExplorer.Core/Abstractions/IProviderCapabilities.cs:8`) keeps describing queue brokers; the web app chooses the tree and the panel by provider type, which is a fact, not a flag.

**This needs an ADR before any code**, because it changes the wording of a lettered rule and an invariant page. The ADR must decide:

- The shape: option 1, 2 or 3; if 3, the name and the exact members of the base contract, and the new sentence of Rule F and of [[pages/invariants/provider-boundaries]].
- The `ProviderType` values (`AzureEventHubs`, `AzureEventGrid`; whether Event Grid is one type or two, namespace and topic), with the four factory switches that throw on an unknown value (`src/ServiceBusExplorer.Core/Providers/ProviderFactory.cs:37`, `src/ServiceBusExplorer.Core/Providers/ProviderFactory.cs:80`, `src/ServiceBusExplorer.Core/Providers/ProviderFactory.cs:101`, `src/ServiceBusExplorer.Core/Providers/ProviderFactory.cs:190`).
- Where the shared Azure pieces live. `Providers/Azure/` is the Service Bus provider today, and the credential factory takes the Service Bus config (`src/ServiceBusExplorer.Core/Providers/Azure/AzureCredentialFactory.cs:25`), whose provider type and DNS suffix are fixed (`src/ServiceBusExplorer.Core/Providers/Azure/AzureConnectionConfig.cs:11`). Proposal: the credential factory and the discovery service stay in `Providers/Azure/` and take a neutral credential description; nothing is renamed.
- The active provider: stay at one per process for this version, or key the slot by connection id now.
- The fate of the Angular provider registry and shell, dead code that reads as the extension point (`web-app/src/app/providers/provider-registry.service.ts:57`); with four products the panel is chosen somewhere, and a plain switch on provider type in the container does it without the registry.

**One active provider per API process.** The active provider is one static field (`src/ServiceBusExplorer.Api/Controllers/ConnectionsController.cs:24`) read through a static accessor typed as `IMessagingProvider` (`src/ServiceBusExplorer.Api/Controllers/ConnectionsController.cs:412`); connecting replaces it for every caller (`src/ServiceBusExplorer.Api/Controllers/ConnectionsController.cs:59`). For a family this means: connecting to an Event Hubs namespace disconnects the Service Bus namespace, so the user sees the three products in one list and one at a time in the tree. That is acceptable for the first version if the screen says so, and it is the limit the alternative connection model removes. Two consequences to handle whichever way the ADR goes: the slot's type becomes the base contract, and the monitoring poller, which calls `GetQueuesAsync` on whatever is connected (`src/ServiceBusExplorer.Api/Monitoring/MonitoringBackgroundService.cs:39`, `src/ServiceBusExplorer.Api/Monitoring/MonitoringBackgroundService.cs:52`), must skip a provider that has no queues instead of failing every 30 seconds.

## The items

"Tests" always means: unit tests in the two unit projects against a mocked SDK client, one failing-call test per new external call (Rule I), a test against the emulator where one exists, and a spec per new component. Every route sits behind the key middleware like the others ([[pages/invariants/local-authenticated-api]], Rule A); no item adds a listener, a CORS origin or an unauthenticated path.

### D1. Sign in and discover the Azure resources

- **Reference tool:** its Event Grid screen asks the user to type subscription id, resource group and namespace name; no discovery.
- **Exists:** the five credential types (`src/ServiceBusExplorer.Core/Providers/Azure/AzureCredentialFactory.cs:25`); nothing references `Azure.ResourceManager`; no endpoint lists anything.
- **Core:** a discovery service in `Providers/Azure/` returning neutral records (subscription, product, kind, name, resource group, location, resource id, endpoint). Recommended call: Azure Resource Graph, `TenantResource.GetResourcesAsync(ResourceQueryContent)` (ARG) with one query over the seven resource types (`microsoft.servicebus/namespaces`, `microsoft.eventhub/namespaces`, `microsoft.eventgrid/namespaces`, `/topics`, `/domains`, `/systemtopics`, `/partnertopics`), projected to the fields above and ordered by id so that paging works. The query text was composed for this page and not run: not verified. Subscription names come from `ArmClient.GetSubscriptions().GetAllAsync()` (ARM). The alternative, per subscription `GetServiceBusNamespacesAsync`, `GetEventHubsNamespacesAsync` (EH-ARM), `GetEventGridNamespacesAsync`, `GetEventGridTopicsAsync`, `GetEventGridDomainsAsync`, `GetSystemTopicsAsync` (EG-ARM), costs up to six paged calls per subscription and is kept only as the fallback if Resource Graph is refused in a tenant.
- **API:** `POST api/azure/sign-in` (credential type, optional tenant), `GET api/azure/resources`, `POST api/azure/sign-out`. The response holds names and resource ids, no secret.
- **Web:** the sign-in step and the resource picker described above; an identity with nothing to show gets a message that names the missing role, not an empty tree (ADR 0003, consequences).
- **Performance:** Resource Graph answers 1,000 records per page with a skip token (https://learn.microsoft.com/en-us/azure/governance/resource-graph/concepts/work-with-data), so most tenants cost one call plus the subscription listing; the limit is 15 queries per 5 seconds per user (https://learn.microsoft.com/en-us/azure/governance/resource-graph/concepts/guidance-for-throttled-requests). The per-subscription fallback is bounded in parallelism and stays under the ARM read bucket of 250 with a refill of 25 per second (https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/request-limits-and-throttling). The result is cached for the session with a manual refresh; it is never polled.
- **Security:** read-only. Results are limited to what the caller can read (https://learn.microsoft.com/en-us/azure/governance/resource-graph/overview): Reader, or a role whose control actions include the read. The Data Owner roles of Service Bus and Event Hubs do carry `Microsoft.ServiceBus/*` and `Microsoft.EventHub/*` control actions (ROLES-I, ROLES-A); the Data Sender and Data Receiver roles carry no namespace read, so such a user sees an empty tree and keeps the manual path. Whether those two roles surface anything in Resource Graph in practice: not verified. Rule G: the token and the credential stay in the provider folder; the client secret of a service principal is already a masked field. Rule F: no `Azure.ResourceManager` type crosses into a controller or a model. Discovery never calls a `listKeys` action.
- **Sovereign clouds:** `ArmClientOptions.Environment` takes `ArmEnvironment.AzurePublicCloud`, `AzureGovernment` or `AzureChina` (https://github.com/Azure/azure-sdk-for-net/blob/main/sdk/resourcemanager/Azure.ResourceManager/src/ArmEnvironment.cs), and the interactive credential names the public cloud today (`src/ServiceBusExplorer.Core/Providers/Azure/AzureCredentialFactory.cs:54`). Same rule as item 12 of the Service Bus page: a fixed list, never a typed URL, and only on request.
- **Depends on:** F1, F4.

### Event Hubs

#### EH1. Connect and list the hubs

- **Reference tool:** lists the hubs of a namespace through the legacy namespace manager; create, update, delete, enable and disable, authorization rules, XML export and import of definitions.
- **Exists:** nothing. The Service Bus connect path is the model: one client per connection, built from a connection string or from a namespace and a credential (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs:109`).
- **Core:** the Event Hubs provider. Connect keeps the namespace, the credential or connection string and, when given, the hub name. Test connection: `EventHubProducerClient.GetEventHubPropertiesAsync` on one hub (EH-API). List hubs, discovered connections only: `EventHubsNamespaceResource.GetEventHubs()` then `EventHubCollection.GetAllAsync(skip, top)` (EH-ARM), mapping `EventHubData.PartitionCount`, `Status`, `CreatedOn`, `UpdatedOn`, `RetentionDescription.RetentionTimeInHours` and whether `CaptureDescription` is set. Manual connections show the one hub the user named and an "add hub by name" action.
- **API:** `GET api/eventhubs`, `GET api/eventhubs/{hub}`.
- **Web:** the tree: hub, then Partitions and Consumer groups; a hub panel with partition count, retention, status and dates.
- **Performance:** one paged management call for the whole namespace, up to 1,000 per page (https://learn.microsoft.com/en-us/rest/api/eventhub/event-hubs/list-by-namespace); a namespace holds 10 hubs on Basic and Standard, 100 per processing unit on Premium, 1,000 on Dedicated (EH-QUOTA). The list never opens an AMQP link per hub.
- **Security:** read-only. Data plane: Azure Event Hubs Data Receiver or the Listen claim to read, Data Sender or Send to publish (https://learn.microsoft.com/en-us/azure/event-hubs/authorize-access-azure-active-directory, https://learn.microsoft.com/en-us/azure/event-hubs/authorize-access-shared-access-signature). Which data role the properties calls need: not verified. Rule G: the connection string is never logged, as on the Service Bus path (`src/ServiceBusExplorer.Core/Providers/Azure/AzureServiceBusProvider.cs:71`). Authorization rules, which the reference tool edits, are keys: not listed, not edited.
- **Depends on:** F1 to F3; D1 for the listing.

#### EH2. Hub and partition details

- **Reference tool:** per partition: id, size in bytes, begin and end sequence number, incoming and outgoing bytes per second, last enqueued offset and time.
- **Core:** `GetPartitionIdsAsync`, then `GetPartitionPropertiesAsync(partitionId)` per partition, returning `PartitionProperties`: `Id`, `IsEmpty`, `BeginningSequenceNumber`, `LastEnqueuedSequenceNumber`, `LastEnqueuedOffsetString`, `LastEnqueuedTime` (EH-API). The numeric `LastEnqueuedOffset` is obsolete: an offset is a string in every model of this feature (the change came with geo-replication, https://learn.microsoft.com/en-us/azure/event-hubs/geo-replication). `EventHubProperties.IsGeoReplicationEnabled` is shown read-only. Size and rates per partition are not in the current client and are not offered.
- **API:** `GET api/eventhubs/{hub}/partitions`.
- **Web:** a partitions table: id, first and last sequence number, an approximate event count (last minus first plus one, labelled approximate), last enqueued time, empty or not. Virtualised ([[pages/conventions/ui]] rule 11): a Dedicated hub can have 1,024 partitions (EH-QUOTA).
- **Performance:** one call per partition, with no batch overload (EH-API): 32 calls on Standard, up to 100 on Premium. Bounded parallelism (8), one shared connection, the caller's token honoured. The service allows 50 runtime information calls per second per consumer group (EH-QUOTA), so the table refreshes on demand and has no timer; a refresh in flight is not restarted.
- **Security:** read-only; no body is read.
- **Depends on:** EH1.

#### EH3. Consumer groups

- **Reference tool:** create, update, delete, user metadata; a listener per consumer group.
- **Core:** management plane only; the data plane has no member for it (EH-API, by absence). `EventHubResource.GetEventHubsConsumerGroups()`, then `GetAllAsync(skip, top)`, `CreateOrUpdateAsync(WaitUntil, name, EventHubsConsumerGroupData)` and `EventHubsConsumerGroupResource.DeleteAsync(WaitUntil)`; data: `UserMetadata`, `CreatedOn`, `UpdatedOn` (EH-ARM). `$Default` always exists (`EventHubConsumerClient.DefaultConsumerGroupName`, EH-API).
- **API:** `GET`, `POST`, `DELETE` under `api/eventhubs/{hub}/consumergroups`.
- **Web:** a list under the hub; create with a name and metadata; delete in a menu, apart ([[pages/conventions/ui]] rule 6). A manual connection shows `$Default` and a field to type another name. The first version can ship the list alone; create and delete are the second step.
- **Performance:** one paged call per hub, read when the node is opened; 1 group per hub on Basic, 20 on Standard, 100 on Premium, 1,000 on Dedicated (EH-QUOTA).
- **Security:** the Data Owner role carries `Microsoft.EventHub/*` control actions and Data Receiver only the consumer group read (ROLES-A); whether plain Contributor is enough: not verified. Deleting a consumer group that a production reader uses breaks that reader and discards the meaning of its checkpoints: typed-name confirmation naming the group, the hub, the namespace and the environment. Creating one is the safe way to read without competing for reader slots (EH4), and the create dialog says so.
- **Depends on:** EH1, D1.

#### EH4. Read events from a position

The core feature.

- **Reference tool:** a "listener" per partition or per consumer group: a legacy event processor registered per partition, with an epoch option, start by offset or by time, client-side checkpoints written to a JSON file, statistics and a chart. No start by sequence number.
- **Exists:** nothing; the nearest shapes are the bounded peek and the bounded search of the Service Bus provider ([[pages/services/core]]).
- **Core:** one bounded read: hub, partition, consumer group, position, maximum events, maximum wait. `EventHubConsumerClient.ReadEventsFromPartitionAsync(partitionId, EventPosition, ReadEventOptions, CancellationToken)` (EH-API) with `EventPosition.Earliest`, `Latest`, `FromSequenceNumber(long, isInclusive)`, `FromOffset(string, isInclusive)` or `FromEnqueuedTime(DateTimeOffset)`, and `ReadEventOptions.MaximumWaitTime` and `PrefetchCount` set from the request. The loop ends at the event count, at a deadline carried by a linked token, or on the caller's token, whichever is first; the deadline is a guard that fires even when the hub is silent ([[pages/invariants/a-guard-must-be-able-to-fire]]). The answer carries the events, the sequence number to continue from, and whether the end of the partition was reached, judged against `LastEnqueuedSequenceNumber`. "Last N events" is one properties call and a read from the last sequence number minus N, clamped to the first. `PartitionReceiver.ReceiveBatchAsync(maximumEventCount, maximumWaitTime, ct)` in `Azure.Messaging.EventHubs.Primitives` (EH-API) is the alternative with the bound in its signature; that it fits better is an inference, not a documented statement, and the choice is made with the emulator in front of the implementer.
- **Never:** a checkpoint (the consumer client has no checkpoint member, EH-API); `ReadEventOptions.OwnerLevel`, which must stay null, since an exclusive reader disconnects every other reader of the partition (https://github.com/Azure/azure-sdk-for-net/blob/main/sdk/eventhub/Azure.Messaging.EventHubs/src/Consumer/ReadEventOptions.cs, https://learn.microsoft.com/en-us/azure/event-hubs/event-hubs-features); `EventProcessorClient`, which needs a blob container to persist checkpoints and claims partition ownership within the consumer group (https://github.com/Azure/azure-sdk-for-net/blob/main/sdk/eventhub/Azure.Messaging.EventHubs.Processor/README.md). `Azure.Messaging.EventHubs.Processor` is therefore not justified and is not referenced.
- **Model:** a neutral event: partition id, sequence number, offset as a string, enqueued time, partition key, message id, correlation id, content type, application properties, system properties, body and body size, from `EventData.SequenceNumber`, `OffsetString`, `EnqueuedTime`, `PartitionKey`, `MessageId`, `CorrelationId`, `ContentType`, `Properties`, `SystemProperties`, `EventBody` (EH-API). It is not forced into `IMessage`.
- **API:** `POST api/eventhubs/{hub}/partitions/{id}/read` with the position, the count (default 50, cap 500) and the wait (default 5 s, cap 30 s) clamped at the boundary; `HttpContext.RequestAborted` passed through, as the batch actions do (`src/ServiceBusExplorer.Api/Controllers/QueuesController.cs:375`).
- **Web:** an events view: partition, consumer group, position picker (earliest, latest, last N, sequence number, time), Read, Read next, a virtualised list, a detail pane with body and properties, a client-side filter over what is loaded. Reading every partition is the same call per partition with bounded parallelism, merged by enqueued time and labelled as merged. A live tail is Read next on a timer with a floor that stops when the view closes, as item 10 of the Service Bus page.
- **Performance:** one AMQP link per read, closed when the call ends; the prefetch is set to the requested count so the client does not buffer events nobody asked for. At most 5 non-exclusive readers per partition per consumer group (EH-QUOTA and the SDK README, https://github.com/Azure/azure-sdk-for-net/blob/main/sdk/eventhub/Azure.Messaging.EventHubs/README.md; the two word the scope differently, so per partition is not verified): the tool holds one slot for seconds, and a quota failure is reported as "this consumer group has no free reader on this partition", with the advice to use a group of its own. Reading spends the namespace's egress allowance, 2 MB per second or 4,096 events per second per throughput unit, and egress is slowed, not refused (EH-QUOTA, https://learn.microsoft.com/en-us/azure/event-hubs/event-hubs-scalability): the caps exist so the tool cannot starve a production consumer in silence. An event is up to 1 MB, 20 MB on Dedicated (EH-QUOTA), so the response is also capped in bytes and the list shows a body preview with the full body on demand.
- **Security:** read-only on the broker: nothing is removed, locked or checkpointed, which is why Rule H does not bind this item and why no confirmation is needed. Event bodies are production data: never written to a log, never held after the response. Rule F: `EventData` and `EventPosition` stay in the provider folder.
- **Depends on:** EH1, EH2.

#### EH5. Send test events

- **Reference tool:** send with body, properties, partition key or a chosen partition, count, sender tasks, batch, think time, body from files and templates, pluggable generators.
- **Core:** `EventHubProducerClient.CreateBatchAsync(CreateBatchOptions)` with `PartitionKey` or `PartitionId`, never both (https://github.com/Azure/azure-sdk-for-net/blob/main/sdk/eventhub/Azure.Messaging.EventHubs/src/Producer/SendEventOptions.cs), `EventDataBatch.TryAdd`, `SendAsync(EventDataBatch)` (EH-API). The batch learns the size limit from the service: 256 KB on Basic, 1 MB on Standard and Premium, 20 MB on Dedicated (EH-QUOTA). An event that does not fit an empty batch is refused with its index, never truncated.
- **API:** `POST api/eventhubs/{hub}/events` with one event or a list, the partition key or id, and a hard cap on the count.
- **Web:** a send dialog: body, content type, properties, partition key or partition, count with a sequence placeholder; the same body editor as the Service Bus send.
- **Performance:** one producer for the operation, batches filled to the limit, progress and cancellation between batches. Above the throughput units the service answers `EventHubsException` with reason `ServiceBusy` (https://learn.microsoft.com/en-us/azure/event-hubs/event-hubs-scalability): the operation stops and reports, and does not retry in a loop of its own.
- **Security:** an event that was sent cannot be deleted; it stays for the retention period and every consumer group of the hub will read it. The confirmation says exactly that and names the hub, the namespace and the environment; above a threshold it asks for the hub's name typed. In the spirit of Rule H: the result is per batch (sent, failed, outcome unknown), and a batch whose send timed out is reported as possibly sent and is never resent in silence.
- **Depends on:** EH1.

#### EH6. Export events

- **Reference tool:** save selected received events as JSON.
- **Exists:** the message export service of the web app writes JSON, CSV and XLSX from what is loaded (`web-app/src/app/core/services/message-export.service.ts:26`).
- **Build:** export of the events loaded in the view, client side, through that service with the event model. No server-side export of a whole partition: with 90 days of retention it has no bound.
- **Security:** an export is production data on the user's disk; the action says how many events it writes. No secret is part of an event model.
- **Depends on:** EH4.

#### EH7. Create and delete hubs: only on request

The reference tool has it. Through `EventHubCollection.CreateOrUpdateAsync(WaitUntil, name, EventHubData)` and `EventHubResource.DeleteAsync` (EH-ARM). Deleting a hub destroys every event in it; partition count cannot be lowered. It needs a control-plane write role and the incident-grade confirmation. Not in the first version: the product is an explorer first, and the portal and infrastructure code already do this.

#### EG1. Connect and list topics

- **Exists:** nothing.
- **Core:** the Event Grid provider, in two kinds. Namespace: `EventGridNamespaceResource.GetNamespaceTopics()`, with `NamespaceTopicData.EventRetentionInDays`, `InputSchema`, `ProvisioningState`. Manual connection: an endpoint plus a key or a credential, and a topic name for a namespace; it can publish (EG3) and, with a subscription name, receive (EG4), and lists nothing. Test connection for a discovered resource is one management read; a manual publish-only connection cannot be tested without publishing, and the screen says so.

- **Security:** read-only. #### EG2. Event subscriptions, with filters and destinations (read-only)

- **Reference tool:** namespace subscriptions only: create and delete, delivery mode, event types, a filter builder for the string, number and boolean operators.
- **Core:** push side: `EventGridTopicResource.GetTopicEventSubscriptions()` and the system topic, domain and domain topic equivalents, or `ArmClient.GetEventSubscriptions(scope)` for any scope; the resource type is `EventSubscriptionResource` and the data class `EventGridSubscriptionData`: `Destination` (webhook, event hub, storage queue, Service Bus queue or topic, hybrid connection, Azure function, monitor alert, namespace topic), `Filter` (`SubjectBeginsWith`, `SubjectEndsWith`, `IncludedEventTypes`, `AdvancedFilters`, `IsSubjectCaseSensitive`), `DeadLetterDestination` (`StorageBlobDeadLetterDestination`: `ResourceId`, `BlobContainerName`), `RetryPolicy` (`MaxDeliveryAttempts`, `EventTimeToLiveInMinutes`), `EventDeliverySchema`, `Labels`, `ExpireOn`, `ProvisioningState` (EG-ARM). Namespace side: `NamespaceTopicResource.GetNamespaceTopicEventSubscriptions()`, with `DeliveryConfiguration.DeliveryMode` (queue or push), `Queue.ReceiveLockDurationInSeconds`, `Queue.MaxDeliveryCount`, `Queue.EventTimeToLive`, `Queue.DeadLetterDestinationWithResourceIdentity`, `FiltersConfiguration.Filters` and `IncludedEventTypes` (EG-ARM).
- **API:** `GET api/eventgrid/topics/{topic}/subscriptions`, `GET .../subscriptions/{name}`.
- **Web:** a subscription panel in three cards: where events go (destination kind and target), which events (filters, as readable sentences), what happens on failure (retry policy, dead-letter destination). Read-only text ([[pages/conventions/ui]] rule 8). A destination that is a Service Bus queue or an event hub the user has a connection for links to it: the one place the family is more than a list.
- **Performance:** one paged call per topic, on demand. Delivery attributes are a separate call per subscription (`GetDeliveryAttributesAsync`, EG-ARM), made only when the panel opens, never in the list.
- **Security:** read-only. Rule G: a webhook destination is shown by its `BaseEndpoint` only; the full URL carries the caller's secret in its query string, is marked secret in the API definition (https://github.com/Azure/azure-rest-api-specs/blob/main/specification/eventgrid/resource-manager/Microsoft.EventGrid/EventGrid/stable/2025-02-15/EventGrid.json), and `GetFullUriAsync` is never called. Delivery attribute values are shown by name with the value masked until it is established how the SDK marks a secret one: not verified. Roles: EventGrid Contributor reads everything; EventGrid EventSubscription Reader lists event subscriptions but its listed actions cover neither topics nor the per-topic subscription path (ROLES-I), so Reader is the role to recommend.
- **Not in the first version:** create, edit and delete of event subscriptions. A filter edited wrongly drops events at the router with no trace; that deserves its own item and confirmation, after the read-only view has been used.
- **Depends on:** EG1, D1.

#### EG3. Publish a test event

- **Reference tool:** publish a CloudEvent with source, type and a JSON payload to a namespace topic.
- **Core:** push topics: `EventGridPublisherClient(Uri, AzureKeyCredential | AzureSasCredential | TokenCredential)` and `SendEventAsync` or `SendEventsAsync` with `EventGridEvent` or `CloudEvent` (EG-API). Namespace topics: `EventGridSenderClient(Uri, topicName, AzureKeyCredential | TokenCredential)` and `SendAsync(CloudEvent)` or `SendAsync(IEnumerable<CloudEvent>)` (NS-API); they accept CloudEvents 1.0 only (https://learn.microsoft.com/en-us/azure/event-grid/concepts-event-grid-namespaces). A push topic has one input schema fixed at creation (`EventGridTopicData.InputSchema`, EG-ARM): a discovered connection selects the form from it; a manual one asks. A domain needs the `topic` property in the Event Grid schema and uses `source` in CloudEvents (https://learn.microsoft.com/en-us/azure/event-grid/event-domains). Custom input schema is not offered at first.
- **API:** `POST api/eventgrid/topics/{topic}/events` with the schema, the fields and a capped count.
- **Web:** a publish dialog with two forms: Event Grid schema (subject, event type, data version, data) and CloudEvents (source, type, subject, data, content type); id and time are generated and shown.
- **Performance:** one request per batch; a batch is at most 1 MB and an event at most 1 MB, billed in 64 KB steps (https://learn.microsoft.com/en-us/azure/event-grid/post-to-custom-topic); 5,000 events per batch on a custom topic and 1,000 per request on a namespace topic (EG-QUOTA).
- **Security:** publishing to a push topic fires every matching subscription at once: webhooks, functions, queues. It cannot be recalled, and the tool cannot see who received it. The confirmation names the topic, the resource and the environment and, when the management plane is available, the number of event subscriptions that will be evaluated. Role: EventGrid Data Sender, data action `Microsoft.EventGrid/events/send/action` (ROLES-I). Rule G: a pasted key or SAS is stored masked. Rule F: `CloudEvent` and `EventGridEvent` stay in the provider folder.
- **Depends on:** EG1.

#### EG4. Namespace topics: receive, acknowledge, release, reject

- **Reference tool:** receive up to 100 events with a wait time, show id, source, type, data; multi-select, then acknowledge, release or reject by lock token, logging success and failure per token. No renew.
- **Core:** `EventGridReceiverClient(Uri, topicName, subscriptionName, AzureKeyCredential | TokenCredential)`; `ReceiveAsync(maxEvents, maxWaitTime, ct)` returning `ReceiveResult.Details`, each a `ReceiveDetails` with `Event` and `BrokerProperties.LockToken` and `DeliveryCount`; `AcknowledgeAsync(lockTokens)`, `ReleaseAsync(lockTokens, ReleaseDelay)`, `RejectAsync(lockTokens)`, `RenewLocksAsync(lockTokens)`, each returning `SucceededLockTokens` and `FailedLockTokens` with an error per token (NS-API). A new neutral result keyed by lock token; `BatchOperationResult` is keyed by a numeric sequence number (`src/ServiceBusExplorer.Core/Models/BatchOperationResult.cs:21`) and is not bent to fit.
- **The fact that shapes the item: there is no peek.** The operations are receive, acknowledge, release, reject and renew lock, nothing else (https://learn.microsoft.com/en-us/azure/event-grid/concepts-event-grid-namespaces). Looking at an event means locking it for 60 to 300 seconds (https://learn.microsoft.com/en-us/rest/api/eventgrid/controlplane/namespace-topic-event-subscriptions/create-or-update?view=rest-eventgrid-controlplane-2025-02-15), during which the real consumer does not get it, and it counts as a delivery attempt (inferred from `DeliveryCount`; not verified). A subscription's maximum delivery count is small (1 to 10 is documented for namespace push delivery, https://learn.microsoft.com/en-us/azure/event-grid/namespace-delivery-retry; the range for queue delivery is not verified), so a look followed by a release can be the attempt that dead-letters the event, or drops it when no dead-letter destination is set (the drop is not verified verbatim).
- **Safety rules, matching Rule H:**
  1. Receive is a state-changing action. Its confirmation names the subscription, the topic, the namespace and the environment, and shows the lock duration, the maximum delivery count and whether a dead-letter destination exists, read from the management plane; on a manual connection it says these are unknown.
  2. Nothing is acknowledged or rejected by default. Closing the view releases every lock still held with `ReleaseDelay.NoDelay` and reports the tokens that could not be released; a lock that simply expires returns the event to the subscription.
  3. Acknowledge deletes the event from the subscription: typed acknowledgement, the count shown. Reject is worse: "Rejected events are dead-lettered if a dead-letter destination is available. Otherwise, they're dropped" (EG-PULL), and the confirmation says which of the two will happen.
  4. Every outcome is reported per event from `SucceededLockTokens` and `FailedLockTokens`; a token that failed is never retried in silence, and an expired lock is reported as "the event went back to the subscription".
  5. Receive is bounded by the service, 1 to 100 events and 10 to 120 seconds of wait (doc comments of the client, https://github.com/Azure/azure-sdk-for-net/blob/Azure.Messaging.EventGrid.Namespaces_1.1.0/sdk/eventgrid/Azure.Messaging.EventGrid.Namespaces/src/Generated/EventGridReceiverClient.cs), and the caller's token is honoured; there is no "receive all" and no purge.
  6. The screen recommends an event subscription of the tool's own on the same topic: each subscription gets its own copy, so the production consumer is never touched. Creating one is the first management write worth adding after this item.
- **API:** `POST .../subscriptions/{sub}/receive`, `POST .../acknowledge`, `POST .../release`, `POST .../reject`, each taking lock tokens in the body. Lock tokens are opaque strings returned to the app and sent back; the API holds no lock state.
- **Web:** a receive view: count and wait, the list with the delivery count per event and a countdown to the lock expiry, a detail pane, and three actions on the selection at different weights: release is routine, acknowledge and reject sit apart in the error colour ([[pages/conventions/ui]] rule 6).
- **Performance:** one HTTP call per action; no polling loop; renew is offered as an explicit action, never automatic, so a forgotten window cannot hold production events locked.
- **Security:** role: the data action `Microsoft.EventGrid/events/receive/action` exists (https://learn.microsoft.com/en-us/azure/role-based-access-control/permissions/integration); the built-in role that carries it, named "Event Grid Data Receiver" in the Python SDK readme (https://learn.microsoft.com/en-us/python/api/overview/azure/eventgrid-readme), is absent from the built-in roles reference: not verified. Event bodies are never logged.
- **Depends on:** EG1; EG2 for the values the confirmation shows.

#### EG5. Dead-lettered events in storage: out for this version

- **What it would be:** a push subscription dead-letters to a blob container, one JSON array of events per blob under `<container>/<SUBSCRIPTION NAME IN UPPER CASE>/<year>/<month>/<day>/<hour>/<guid>.json`, each event carrying `deadLetterReason`, `deliveryAttempts`, `lastDeliveryOutcome` (https://learn.microsoft.com/en-us/azure/event-grid/manage-event-delivery, https://learn.microsoft.com/en-us/azure/event-grid/delivery-and-retry). A namespace subscription does the same under `<container>/<namespace>/<topic>/<subscription>/...` (https://learn.microsoft.com/en-us/azure/event-grid/dead-letter-event-subscriptions-namespace-topics).
- **Why out:** reading it is reading Azure Blob Storage: a fourth Azure service, a storage SDK that is not on the owner's list of libraries (the `Azure.Storage.Blobs` API was not checked: not verified), a role on a different resource (Storage Blob Data Reader, https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles/storage), a listing with no natural bound, and a storage account that usually holds other data. It is a blob browser, not a messaging feature.
- **What ships instead:** EG2 shows the dead-letter destination (account, container and the expected path prefix) with a copy action, so the user opens it in a storage tool. Resubmitting a dead-lettered event is then EG3 with a pasted body.
- **Revisit when:** a user asks, and the owner admits the storage SDK.

- **Event Hubs data plane.** Microsoft publishes an emulator: `mcr.microsoft.com/azure-messaging/eventhubs-emulator`, tags `2.2.1`, `2.2.0`, `2.1.0`, `2.0.1` and `latest`, for amd64 and arm64 (https://mcr.microsoft.com/v2/azure-messaging/eventhubs-emulator/tags/list). Limits: 1 namespace, 10 hubs, 32 partitions and 20 consumer groups per hub, 1 MB per event (EH-EMU). The connection string ends in `UseDevelopmentEmulator=true` (https://learn.microsoft.com/en-us/azure/event-hubs/test-locally-with-event-hub-emulator). The fixture pins `2.2.1`, as the Service Bus fixture pins its image, and follows [[pages/decisions/0002-integration-tests-against-brokers-in-docker]]: the connection comes only from the container, no Docker fails the run. Whether a Testcontainers module for it exists at the version the project uses (`src/ServiceBusExplorer.IntegrationTests/ServiceBusExplorer.IntegrationTests.csproj:18`): not verified; a generic container with the two images is the fallback.
- **Covered there:** EH4 in full (every position, the bound, the deadline, cancellation, read next, last N), EH5 (batches, partition key, partition id, an oversized event), the model mapping, and EH2 if the emulator answers the properties calls, which the official sample does not exercise: not verified, and the first thing the fixture establishes.

**What no container can test.**

- **Every management-plane call:** listing hubs, consumer group create and delete, D1, EG1, EG2, M. The Event Hubs emulator supports no management operation from an SDK, entities come from the configuration file only, and it has no Entra ID (EH-EMU). There is no emulator of Azure Resource Manager, Resource Graph or Azure Monitor.
- **Event Grid, all of it.** Microsoft publishes no Event Grid emulator: a search of Microsoft Learn finds none, and the one repository under the Azure organisation, `Azure/eventgrid-emulator`, is archived, last pushed in 2018 and predates namespaces (https://github.com/Azure/eventgrid-emulator). Community projects exist: `pm7y/AzureEventGridSimulator` (push topics, no pull delivery in its README, https://github.com/pm7y/AzureEventGridSimulator) and `workleap/wl-eventgrid-emulator` (a container with push and pull for namespace topics, not affiliated with Microsoft, https://github.com/workleap/wl-eventgrid-emulator); their fidelity with the SDK clients was not tested.
- **Also untested by any container:** Entra credentials and role refusals, throttling, the reader limit, tier limits above the emulator's, geo-replicated offsets.

**The proposal for what cannot be tested in a container.** ADR 0002 forbids a skipped test and a test against a broker the run did not start, and its point 6 says that what an emulator cannot do is written down, not worked around. So:

1. **Unit tests against the SDK's own seams carry the management plane and Event Grid.** The clients are mockable, as the Service Bus tests already mock receivers, senders and the administration client; each provider method takes its client through a static seam like the existing ones ([[pages/services/core]]). Each call gets its mapping test and its failing-call test (Rule I): a refused role, a missing resource, a timeout, a throttled request, a per-token failure. The model factory types needed to build SDK results in tests are not verified per type.
2. **The gap is recorded** on [[pages/conventions/testing]] in the form of its "What the emulator cannot do" list: Event Grid and the management plane are untested by integration, with the reason. `reliability: medium` on the service page until that changes.
3. **A manual verification script per item**, run by the owner against a throwaway resource group he names for that purpose, and its result recorded in the pull request. It is a checklist, not an automated test: nothing in the repository holds a subscription id, a namespace or a credential, which is the rule of the root `CLAUDE.md` and of ADR 0002 point 2. This is the "reproduction against a real broker is manual" clause of the testing convention, applied.
4. **A community Event Grid emulator in the integration project is the owner's decision**, not a default: a third-party image in CI is a supply-chain choice (pinned by digest if admitted), and a pass against it proves this code against that project's reading of the protocol. It would cover EG3 and EG4 only.
5. **No nightly run against real Azure.** It would put a credential in CI for a public repository and break the rule the ADR exists for.

## Order

Each phase ships something a user can use.

1. **Phase 0: decisions.** The ADR (F1), the open questions below, the screens on the prototype ([[pages/conventions/ui]]). No code.
2. **Phase 1: Event Hubs by connection string.** F2, F3, F6, F7, then EH1 for one named hub, EH2, EH4, EH5, EH6. Usable alone: connect to a hub, see its partitions, read from any position, send. The whole phase is tested on the emulator.
3. **Phase 2: sign in and discover.** F4, D1, then the hub list of EH1 and EH3 (list first, create and delete after). This also delivers ADR 0003's missing half for Service Bus, with no change to the Service Bus provider.
4. **Phase 3: Event Grid, read and publish.** EG1, EG2, EG3. Usable alone: see where every event of a topic goes and why, and publish a test event.
5. **Phase 4: Event Grid pull.** EG4, with its safety rules; then, if wanted, creating the tool's own event subscription.
6. **Phase 5: on request.** M, EH7, event subscription editing, EG5, sovereign clouds, the single "Azure account" connection once several providers can be active.

Each phase is a pipeline lane with its own tests and review lenses: `boundaries` on every phase (Rule F is being reworded), `secrets` on phases 2 to 4 (credentials, keys, webhook URLs), `message-safety` on EH5 and all of phase 4, `api-surface` on every new controller.

## Open questions for the owner

- **Which product first?** This page orders Event Hubs first: it has an emulator, so its core feature can be proven, and it works with a connection string before discovery exists. Event Grid first is possible only with the management plane, that is, after discovery.
- **One connection per resource under one sign-in (recommended), or one "Azure account" connection with everything under it?** The second needs several active providers per API process first.
- **The provider shape:** option 3 as recommended, which rewords Rule F, or one of the other two? The ADR is the next thing to write.
- **Management-plane access.** Listing hubs, consumer groups, topics and event subscriptions, and metrics, needs an Entra identity with Reader on the resources; a connection string or a key gives the data plane only. Is a data-plane-only experience for manual connections acceptable, with the reason shown on screen?
- **`Azure.Monitor.Query` is deprecated.** Move the metrics service to its replacement as part of item M, or sooner as its own change?
- **The undocumented status of the namespace REST listing** (`$Resources/Eventhubs`): confirmed out under "current SDKs only"? It is the only way to list hubs with a connection string.
- **Event Grid receive on production.** EG4 as proposed (confirm, then receive, never acknowledge by default), or receive only from an event subscription the tool created for itself?
- **A community Event Grid emulator in the integration tests:** admit one, or keep Event Grid at unit tests plus a manual checklist?
- **Dead-lettered events in storage:** out as proposed, or admit the storage SDK?
- **Administration** (create and delete hubs, consumer groups, event subscriptions): in the first version, or after the read side has been used?
- **Naming.** The solution, the projects and the connection model are called "ServiceBus"; does a rename wait for a major version, or never happen?
